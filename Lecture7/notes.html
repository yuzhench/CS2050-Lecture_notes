主题：Introduction to MPI（分布式内存并行编程入门）

Lecture 7 的 slide 1–7 是行政内容（课程公告、HW 时间线、上一讲回顾等），这里跳过。技术内容从 slide 8 开始。

Slide 8 — Why Distributed Parallelism?（为什么需要分布式并行）

这一页是 Lecture 7 的开场，承接上一讲的 OpenMP（共享内存）抛出新问题：为什么仅靠一台机器的多线程还不够？答案是单机的内存与算力都有物理上限，而很多真实问题已经超过了这个上限，必须把计算分散到多台机器上。

单机的根本瓶颈：Maximum memory per node is limited

"node"（节点）在 HPC 语境里就是"一台物理服务器"。再高端的服务器内存也只有 1–2 TB 量级，CPU 核心数也就几十到上百个。这个上限是硬件物理限制，不是可以靠"加钱"无限突破的 —— 主板插槽数、内存控制器带宽、单 CPU 的封装尺寸都卡死了天花板。

For large computing tasks, single-node memory is simply not enough

slide 列了四类典型的"装不下"工作负载，都是 HPC 经典应用：

  • Fluid dynamics（计算流体力学） —— 模拟飞机机翼气流、海洋洋流、天气预报。需要把 3D 空间离散成几十亿个网格点（cell），每个 cell 存储速度、压强、密度等。一个高分辨率仿真很容易就要几十 TB 的内存。
  • Molecular dynamics（分子动力学） —— 模拟蛋白质折叠、药物分子结合。每个原子要存位置、速度、受力，蛋白质体系动辄百万原子，每个时间步还要算所有原子两两之间的相互作用。
  • Machine learning（机器学习） —— 训练大模型。GPT 级别的模型有几千亿到万亿参数，参数本身就要几 TB 的显存/内存，加上梯度、优化器状态后翻倍再翻倍。一张 GPU 的 80GB 显存远远不够，必须把模型切片分布到几百上千张 GPU 上。
  • Large scale data processing（大规模数据处理） —— Google 网页索引、Meta 用户日志、CERN 粒子对撞数据，原始数据就是 PB 量级，单机连"读一遍"都不可能。

Solution: Many nodes connected by (HPC) network

右下角紫色框是 slide 给出的解决方案：把多台节点用专用高速网络连起来组成一个集群（cluster / supercomputer）。这就是右上角图片那种数据中心的样子 —— 一排排机柜，每个机柜里几十台服务器。

关键的两点设计选择：

  • Memory is distributed among connected nodes —— 内存是分布在各节点上的，没有任何一块内存是所有节点共享的。这和 OpenMP 的"共享内存"模型本质不同：节点 A 的程序看不见节点 B 的内存，必须通过网络问对方要数据。
  • Communication achieved by sending or receiving messages over the network —— 节点之间通信靠"发消息"，这就是后面要讲的 MPI（Message Passing Interface，消息传递接口）的命名由来。一个节点要对方的数据，就显式地 MPI_Send / MPI_Recv。

HPC network 是什么"专用"

这里的"(HPC) network"不是普通的以太网/Wi-Fi，而是专为低延迟设计的互联网络，常见的有 InfiniBand、Omni-Path、NVLink（GPU 之间）。普通以太网延迟可能在毫秒量级，HPC 网络延迟在微秒级，带宽也高一两个数量级 —— 因为分布式并行的性能瓶颈往往不是计算而是通信，网络慢一点整个程序就拖死了。

💡 核心对比：OpenMP 是"一台机器内多个线程共享同一块内存"；MPI 是"多台机器各有独立内存，靠发消息协作"。前者天花板是单机硬件，后者天花板是你买得起多少机器 + 网络多快。Lecture 7 整章就在讲后者怎么写。

Slide 9 — Orthogonality（共享内存 与 分布式内存 是正交的两个层级）

这一页只讲一句话："Shared memory and distributed memory are two orthogonal programming models"—— 共享内存模型和分布式内存模型是正交的，不是互斥的。"正交"在工程语境里就是"两个独立维度，可以叠加使用"。

图里在说什么

右边的图把一个超算系统拆成两个层级看：

  • Node level（节点层，纵向） —— 每个节点内部是 shared memory + heterogeneous CPU/GPU computing。也就是 Lecture 6 讲的 OpenMP 世界：一台机器内多个核心、多个 GPU，共享同一块物理内存。slide 上半边那个箭头标的"So far we went this way (node level)"就是说前面学过的内容。
  • Cluster level（集群层，横向） —— 多个节点之间通过网络相连，是 distributed memory。Process 0 / Process 1 / Process 2 各跑在不同节点上，靠"Message passing"互通有无。slide 左边的"Now we go this way (cluster level)"就是 Lecture 7 要进入的新世界。

为什么强调"正交"

真实 HPC 程序几乎都是两层都用：节点之间用 MPI 发消息，节点内部再用 OpenMP 多线程把单节点的核心榨干。这种叫 hybrid MPI+OpenMP，是上一讲那张性能曲线里上限最高的蓝线。

所以"正交"的含义是：你不需要二选一。MPI 不替代 OpenMP，它解决的是 OpenMP 解决不了的问题（跨节点）；OpenMP 也不替代 MPI，它专攻 MPI 不擅长的事（节点内细粒度多线程）。

💡 记住坐标系：纵向 = 节点内 shared memory（OpenMP），横向 = 节点间 distributed memory（MPI）。两个维度可以同时使用，这就是后面 Lecture 7 全章的世界观基础。

Slide 10 — Shared vs Distributed Memory（两种内存模型的优缺点对比）

这一页是把 Slide 9 的"两种模型"展开来，对照写出各自的优缺点和承载它们的网络。slide 用左右两栏分别讲 shared 和 distributed，每栏上半是"编程层面的优缺点"，下半是"硬件层面的网络"。

左栏：Shared memory（共享内存）

  • Accessing data is easy（编程容易）—— 所有线程共用同一内存地址空间，一个线程写下的变量另一个线程直接读就行，不需要显式通信。
  • Race conditions（数据竞争）—— Lecture 6 已经踩过这个坑：两个线程同时改同一个变量，结果不确定。"易访问"的代价。
  • False sharing（伪共享）—— 两个线程改的是不同变量，但这两个变量恰好落在同一条 cache line（通常 64 字节）上。CPU 的缓存一致性协议会因此频繁来回同步这条 cache line，性能严重下降。是共享内存特有的"暗坑"。

下半 On-Chip Network (OCN)：

  • Fast communication（极快）—— 因为根本没"通信"，就是一次内存读写。
  • Maximum distance: few centimeters —— 都在同一块主板甚至同一颗芯片里，物理距离几厘米。
  • Examples: memory bus, Intel Ultra Path —— 内存总线、Intel UPI（不同 CPU socket 之间互联的总线）就是典型 OCN。

右栏：Distributed memory（分布式内存）

  • No direct access to distributed data —— 节点 A 的程序拿不到节点 B 的内存地址，根本无法"直接读"。
  • You must take care of communication explicitly —— 所有数据交换必须程序员显式调用 MPI_Send/MPI_Recv。代码量和复杂度比 OpenMP 高一个数量级。
  • No race conditions for distributed communication —— 因为没有共享变量可争抢，所以 race condition 这个 bug 类整个消失了。换句话说：你失去了易用性，但换来了正确性上更好的隔离性。
  • Can scale to much larger number of parallel processors —— 这是分布式的真正优势：可以堆几千上万个节点，OpenMP 永远做不到。

下半 System Area Network (SAN)：

  • Slow communication —— 相对于 OCN 慢得多。延迟从纳秒变成微秒级，差几个数量级。
  • Examples: InfiniBand, Cray Slingshot, Ethernet —— 前两个是专业 HPC 互联（低延迟、高带宽），普通以太网也能凑合用但延迟最高。
💡 一句话总结这页的取舍：共享内存"快但坑多、规模有限"；分布式内存"慢但坑少、规模无上限"。MPI 选的就是后者这条路 —— 用编程复杂度换可扩展性。
Q：False sharing 到底是怎么发生的？为什么逻辑上不冲突的两个线程会互相拖慢？

根因：CPU 按 cache line 读写，不按变量。你写 x = 5，硬件实际把包含 x 的整条 64 字节 cache line拉进自己核心的 L1。粒度比变量大得多 —— 哪怕只想改 4 字节，硬件也搬 64 字节。

缓存一致性的硬规则：多核场景下，任意时刻一条 cache line 最多只能由一个核心持有"修改"权（MESI 协议的 M 状态），其他核心的副本必须先作废。

伪共享在代码里长这样：

int counter[2];   // 2 个 int = 8 字节，几乎一定落在同一 cache line
#pragma omp parallel num_threads(2)
{
    int tid = omp_get_thread_num();
    for (int i = 0; i < 100000000; i++)
        counter[tid]++;   // 看上去：线程独立写各自的变量
}

逻辑上零冲突。物理上发生的事：

Core 0 写 counter[0]   → 抢到 cache line 的修改权
Core 1 想写 counter[1] → Core 0 必须先写回，Core 1 重新拉入并抢权
Core 0 又写            → 反过来再抢一遍
... cache line 在两核之间无限 ping-pong

每次"抢"都要走核间总线，跨 socket 时甚至要走 UPI。延迟从 1 cycle 涨到几十纳秒。一个看起来完美并行的循环，可能比单线程还慢。

修复：让每个线程要写的变量独占一条 cache line。

struct alignas(64) Slot { int value; };   // C++17
Slot counter[2];                          // counter[0] 和 counter[1] 各占一条 line
// 或手动 padding：
struct { int value; char pad[60]; } counter[2];

"伪"在哪里：从代码看两个线程没共享任何变量，从硬件看它们共享了同一条 cache line。这种"程序员看不见但硬件强制存在"的共享，肉眼无法定位，必须靠 perf / VTune 这类 profiler 才能发现。

Slide 11 — Recall: Processes and Threads（重温进程 vs 线程，但更强调"物理位置"）

这一页是为后面的 MPI 做铺垫 —— MPI 的并行单位是进程（process），不是线程。所以先把进程和线程的区别再过一遍，并强调一个容易误解的点。

进程 vs 线程的核心差别（紫色框）

Processes：OS 创建，expensive to create。每个进程都有自己独立的虚拟地址空间（own virtual address space） —— 它看到的指针 0x7fff1234 和别的进程看到的同一个数值指向完全不同的物理内存。这就是为什么进程之间默认不能直接读写对方的内存。

Threads：共享所属进程的资源（地址空间、文件描述符等），less expensive to create。OpenMP 用的就是线程。

关键澄清（左下两条 bullet）

这是这一页真正想纠正的误区："独立虚拟地址空间"≠"独立物理机器"。

  • Does not mean each process must live in a separate physical memory space (or on different nodes) —— 多个进程可以挤在同一台机器、同一块内存里。"独立"只是 OS 给每个进程画的虚拟地图不同，物理上它们的页表都映射到同一块 RAM 上，OS 帮它们隔离。
  • For example, many processes run simultaneously on your laptop —— 你笔记本现在打开 Chrome、VS Code、Slack，是好几个进程在同一台机器上同时跑。它们各有虚拟地址空间，但都用同一块物理 RAM。
  • Does not matter whether these processes originate from individual programs or from a distributed memory code —— OS 不区分"这是普通进程"还是"这是 MPI 的一个 rank"，对它来说都是普通进程。MPI 的"分布式"是编程模型层面的，不是 OS 强制的。

右边两个图的含义

  • Shared memory 图：一个 Process 持有一块 Memory，里面跑两个 Thread —— 线程共享内存。这是 OpenMP 模型。
  • Distributed memory 图：四个 (Process, Memory) 对，通过 Network 相连。slide 注解说这些 Process 可以"run on one or many cores or even somewhere in the cloud" —— 强调 MPI 的进程物理位置无所谓，可以全在一台机器上（用来调试），也可以在地球两端，模型层面都一样。
💡 关键认知：MPI 的"distributed"指编程模型上每个进程逻辑独立、必须显式通信，不意味着进程必须分散在不同机器上。这点重要 —— 它意味着你可以在一台笔记本上启动 4 个 MPI 进程做开发，逻辑和跑在 4 台真机上完全相同。

Slide 12 — Message Passing Interface (MPI)（MPI 究竟是什么）

这一页正式给出 MPI 的定义，并解释"为什么需要它"以及"它在系统栈里处于哪一层"。

问题的起点（左栏前两条）

  • A process cannot access the memory of another process —— 这是OS 层面的硬规则，不是 MPI 的限制。多用户操作系统（Linux/Windows）必须做这种隔离，否则一个程序就能读你银行 App 的内存，安全性崩塌。slide 右上的小图就是 Linux 进程的虚拟地址空间布局（Stack / Heap / Data / Code 四段），每个进程都有这样独立的一份。
  • Communication between processes is important when they cooperate on a problem (e.g. MPI) —— 但科学计算又必须让多进程合作算同一个问题，所以"进程间通信"（IPC）是必需的。

OS 提供的 IPC 机制

Inter-process communication is implemented by the OS with several mechanisms: signals, files, pipes, sockets, or shared memory —— OS 已经提供了一堆 IPC 原语：信号、文件、管道、socket、共享内存段。每个都能跨进程传数据，但是用法各异、跨平台不一致。

核心问题（右栏第一条）

Should we write our own protocols to communicate between processes? No! Would be error-prone, and overkill —— slide 直接给出反问加回答：每写一个并行程序就重新设计通信协议（怎么编码消息、怎么处理乱序、怎么处理失败），既容易出 bug 又是重复造轮子。

MPI 的定位

  • Since such communication is ubiquitous, a standard exists: the Message Passing Interface (MPI) —— 既然大家都要做同一件事，那就定一个标准。这就是 MPI 的诞生动机。
  • MPI specifies an API (Application Programming Interface) —— 注意：MPI 是规范（specification），不是软件。它只规定了"函数应该叫什么名字、参数是什么、做什么事"，不规定"底层用 socket 还是 shared memory 来实现"。
  • The MPI code you write does not depend on a specific implementation. Your code will run on a compute cluster just like it will run on your laptop —— 这是 API/规范分离的好处：你的代码只用 MPI 标准函数，跑在哪个具体实现上都行。
  • All you need is to include the API declarations in your code: #include <mpi.h> —— 用法和普通 C 库一样，#include 头文件，链接 MPI 库就行。

主流实现（左栏底部）

Many different MPI implementations of the specification exist。最常见的几个开源实现（写代码时通常装其中之一就够了）：

  • OpenMPI —— 学术界最常用，社区活跃。
  • MPICH —— 老牌实现，很多商业版本是基于它修改的。
  • MVAPICH —— 针对 InfiniBand 网络做了深度优化。

另外还有 vendor-specific 优化版本：Cray/HPE、Intel、IBM、Microsoft 等大厂会基于自家硬件做定制 MPI（性能比开源版本更好，但只在自家平台上跑）。

💡 记住三件事：(1) MPI 是规范，不是软件；(2) 你装的"OpenMPI/MPICH"才是软件，是 MPI 规范的实现；(3) 同一份代码可以无修改在不同实现间切换 —— 这就是 portability 的来源。
Q：Specification、API、Implementation 三者到底什么区别？

三层不同抽象，分开看就清楚了：

Specification（规范）= 一份纸面文档。规定"应该有哪些函数、参数是什么、做什么事、出错时怎样"。本身不能运行。MPI 的规范是 ~1100 页 PDF，由 MPI Forum 维护。

API= 规范暴露给程序员的函数签名集合，存在于头文件里。你 #include <mpi.h> 之后看到的就是 API：

int MPI_Send(const void *buf, int count, MPI_Datatype datatype,
             int dest, int tag, MPI_Comm comm);

Implementation= 真正写出 MPI_Send 函数体的代码 + 编译出的 libmpi.so。它要决定"消息怎么过网络"（TCP？InfiniBand？同机器走共享内存？）。OpenMPI、MPICH、Intel MPI 各是一个独立项目，几十万行代码，但都满足同一份 spec。

关系：spec ⊃ API。API 是 spec 中给程序员看的部分；spec 还规定了语义、错误行为、进度保证等 API 签名之外的东西。日常说话经常把"MPI API"和"MPI spec"混用。

USB 类比

层级USB 世界MPI 世界
SpecificationUSB 协议文档（形状/电压/字节序）MPI 标准 PDF
APIUSB-A 插口形状（你能怎么插）MPI_Send(...) 函数签名
ImplementationAnker / Belkin 各自做的数据线OpenMPI / MPICH / Intel MPI

手机不在乎你用 Anker 还是 Belkin —— 都是 USB。MPI 程序也不在乎底层链接的是哪家实现 —— 都满足同一份 spec。

同一份代码，跑两种实现

// hello.c —— 一字不改
#include <mpi.h>
int main(int argc, char **argv) {
    MPI_Init(&argc, &argv);
    int rank;
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    printf("Hello from rank %d\n", rank);
    MPI_Finalize();
}

笔记本上装 OpenMPI：

mpicc hello.c -o hello       # mpicc 是 OpenMPI 提供的包装器
mpirun -n 4 ./hello          # 链接 OpenMPI 的 libmpi.so

把一字未改的 hello.c 拷到装 Intel MPI 的集群：

mpicc hello.c -o hello       # mpicc 现在是 Intel MPI 提供的
mpirun -n 64 ./hello         # 链接 Intel MPI 的 libmpi.so

编译器是不同公司的工具、链接进去的 libmpi.so 是完全不同的二进制、底层网络从 shared memory 变成 InfiniBand —— 但观察到的行为完全一致。这就是"Your code will run on a compute cluster just like it will run on your laptop"的实际含义。

Slide 13 — MPI History（MPI 标准的版本演进）

这一页是 MPI 的版本时间线。slide 一笔带过历史，重点是知道存在哪几个主版本以及它们各自加了什么。

背景

1980 年代到 90 年代初，做分布式并行只能用各家不兼容的私有库，移植性、性能、功能、价格各方面都很糟。一个工作组在 Minneapolis 开会起草 MPI 草案（MPI-1），由 MPI Forum 推动 —— 40 多个组织参与，有并行计算机厂商、应用科学家。

主要版本（slide 表格）

版本年份主要变化
1.01994第一个标准，奠定消息传递接口的基础。注意：MPI Forum 不是任何官方标准化组织背书的，是社区自治的。
2.01997加入动态进程创建、单边通信（one-sided communication）、扩展的集合通信、并行 I/O。
3.02012大版本：非阻塞集合通信（non-blocking collectives）、新的单边操作、Fortran 2008 绑定。是相对早期版本的重大扩展。
4.02021新增持久化集合通信、分区通信（partitioned communications）、错误处理改进。

slide 右上角紫色框还提到 MPI 5.0 已于 2025-06-05 由 MPI Forum 批准发布（最新版）。

对学习的实际意义

大多数教程和课程代码都基于 MPI-3.x 写的，因为 3.0 是真正成熟、广泛部署的版本。MPI-1 的核心 API（MPI_Init、MPI_Send、MPI_Recv、MPI_Finalize）30 年来基本没变，所以学最老的 API 也能跑在最新的实现上。

💡 记忆要点：版本号不是细节考点，但要知道"MPI-3 加了非阻塞集合通信"和"MPI-2 加了并行 I/O"这两件大事 —— 后续课程讲性能优化时会经常引用它们。

Slide 15 — Overhead between OpenMP and MPI（两种模型的开销曲线）

这一页用两张图同时讲 开发开销 和 运行开销，比较 OpenMP 和 MPI 在这两个维度上的不同表现。

左图：Time to (parallel) software（开发投入 vs 性能）

横轴是投入的时间和精力，纵轴是程序性能。三条曲线：

  • OpenMP（绿）：从 sequential program 出发，曲线立刻陡升 —— 加几行 #pragma omp 就有加速。但很快趋于平缓，因为它的天花板就是单节点的核心数。优势是"投入小见效快"。
  • MPI（红）：曲线起步是虚线，标注 "Code does not work" —— 一开始改成 MPI，需要重写通信逻辑、处理 rank、设计数据划分，这段时间程序根本跑不起来。slide 紫色框补充：MPI code does not work in initial parallelization phase because communication must be handled explicitly by API calls。但一旦跑通，曲线超过 OpenMP，能扩展到更高性能。
  • MPI+OpenMP（蓝）：投入最大、上限最高的混合模式，HPC 程序的最终形态。slide 紫色框补充：OpenMP code involves API only (compiler directives and some runtime routines), this mostly due to implicit communication —— OpenMP 看起来"轻"，是因为通信被编译器和运行时偷偷做了；MPI 看起来"重"，是因为这些通信被你显式接管了。

右图：Communication overhead（通信开销 vs 问题规模）

横轴是问题规模（problem size），纵轴是需要的 CPU 数（number of CPUs）。

  • 蓝色 Sequential 区：1 个 CPU 就够，问题小，没必要并行。
  • OpenMP 区：CPU 数到 O(10²)，仍在单节点的 OCN（On-Chip Network）上，通信成本几乎为零。
  • MPI 区：CPU 数到 O(10⁵)，跨节点用 SAN（System Area Network），但红色阴影标注 "Dominated by overhead" —— 当节点数太多时，通信开销超过了计算时间，再加节点反而变慢。

slide 紫色框点出关键：SAN can cover larger area at the cost of slower speed (same story with caches, cell phones, etc.) and therefore higher latencies. Hiding these latencies is more difficult the more complex the system becomes. —— 大规模和低延迟是相互拉扯的两个目标，越大的系统越难掩盖延迟。

💡 实战启示：(1) 小规模问题用 OpenMP 性价比最高；(2) 跨节点必须 MPI，但要预留前期"代码不工作"的开发周期；(3) MPI 不是"加越多节点越快"，过了某个临界点通信开销会反噬性能 —— 这就是后面要学的 scaling 分析的动机。

Slide 16 — Why Use MPI?（用 MPI 的五个理由）

这一页是给 MPI 做"销售"，列了五个采用它的理由。每条都很简短，对应理解一遍即可。

  • Standardization（标准化） —— MPI 是唯一能称作标准的消息传递库，被几乎所有 HPC 平台支持。这意味着你学会 MPI，全世界的超算都能用。
  • Portability（可移植性） —— 同一份代码不改或几乎不改就能从一个平台搬到另一个 MPI 兼容平台。这是上一页"specification vs implementation"分离带来的直接好处。
  • Performance opportunities（性能潜力） —— 厂商实现可以利用各自硬件的特性（专用网络、RDMA、GPU 直连）做优化。MPI 标准只规定"做什么"，不限制"怎么做"，留下了优化空间。
  • Functionality（功能丰富） —— MPI-3 定义了 430+ 个函数。但 slide 用紫色框特别强调："Most MPI programs can be written using a dozen or fewer routines"。也就是说常用的就十来个，剩下的都是高级特性，先不必管。
  • Availability（可获得性） —— 既有商业实现也有开源实现（OpenMPI、MPICH 都免费），不会被某个厂商绑定。
💡 对学习者最重要的一条：常用 API 就十来个，所以入门门槛比看起来低 —— 不要被 "430 routines" 吓到。

Slide 17 — MPI Communicators and Groups（通信器与组：MPI 里"谁能跟谁说话"的概念）

这一页引入两个 MPI 的核心抽象：communicator（通信器） 和 group（组）。它们是"哪些进程之间可以通信"的元数据。

三个要点

  • MPI uses objects called communicators and groups to define which collection of processes may communicate with each other —— communicator 和 group 是定义"通信范围"的对象。一个进程不能给任意进程发消息，必须在某个 communicator 内。
  • Most MPI routines require to specify a communicator as an argument —— 几乎所有 MPI 函数（MPI_Send、MPI_Bcast 等）都要传一个 communicator 参数告诉它"这次通信发生在哪个范围内"。这是 MPI API 的一个普遍约定。
  • MPI_COMM_WORLD is the predefined default communicator that includes all of your MPI processes —— 程序启动时 MPI 自动建好一个叫 MPI_COMM_WORLD 的全局 communicator，包含所有进程。最简单的程序只用这一个就够。

An MPI communicator encapsulates（一个 communicator 里到底封装了什么）

  • Contexts（上下文） —— 通信的"宇宙 ID"。两个不同 context 的消息互不干扰，即使涉及同一组进程。这是用来避免不同库之间消息混乱的机制。
  • Groups（组） —— 这个 communicator 里到底有哪些进程。可以是全部进程，也可以是子集。
  • Virtual topologies（虚拟拓扑） —— 进程的逻辑排列方式。例如可以告诉 MPI"把我的 16 个进程当成 4×4 的二维网格"，之后就可以方便地说"给我上面/左边的邻居发消息"，而不用手算 rank 编号。这在写 stencil 计算（如 PDE 求解）时很有用。
💡 第一直觉：communicator = "聊天群"，group = "群成员名单"，rank = "群里的成员编号"。MPI_COMM_WORLD 就是默认的"全员群"。
Q：Group 和 Communicator 不都是"一群进程"吗？Context 到底是什么、长什么样？

1. API 层面的硬区别：group 不能发消息

看一下 MPI_Send 的签名：

int MPI_Send(const void *buf, int count, MPI_Datatype dtype,
             int dest, int tag, MPI_Comm comm);   // 收 MPI_Comm，不是 MPI_Group

API 直接拒绝你拿 group 发消息 —— 没有 MPI_Send_with_group(...) 这种函数。Group 只能用来做本地集合运算（incl / excl / union / intersection / difference），这些操作不走网络、几乎零成本。

维度GroupCommunicator
本质一份进程名单名单 + context_id + topology
能发消息吗❌✅
能做集合运算吗✅（本地、便宜）❌（要先抽成 group）
创建成本几乎零collective 通信，贵

设计上的取舍：先用便宜的 group 自由地做集合运算，等真要通信了再花一次"升级费"做成 communicator。

2. MPI_Comm 在代码里长什么样

它是个 opaque handle（不透明句柄）—— MPICH 里就是个 int（句柄表索引），OpenMPI 里是个指向内部 struct 的指针。你不能也不应该直接访问内部字段，只能通过 MPI_Comm_size() / MPI_Comm_rank() 这类 API 去问它。

如果能"撬开"它（伪代码，非真实 API）：

struct {
    int        context_id;     // 例：0x47 —— 这个 communicator 独有的整数
    MPI_Group  group;          // 名单：[rank0, rank1, ...]
    Topology   topology;       // 可选：例如 4×4 网格 / 环 / 树
    // ... 内部簿记
}

3. Context 不是哲学，就是一个整数标签

由 MPI 库在创建 communicator 时自动分配，全局唯一，你看不到也不需要看到。它的作用：塞进每条消息的 envelope（信封），让接收方能匹配"这条消息属于哪条频道"。

回忆 message envelope 字段：[source | dest | communicator | tag | dtype | count] —— 实际放进信封的是 communicator 的 context_id 这个整数。接收方匹配时：

进来消息.context_id == 我 Recv 时传入的 comm.context_id ?
不等 → 忽略
相等 → 才看 source / tag

两个不同的 communicator = 两个不同的 context_id = 两条互相隔离的频道。哪怕它们包同一组进程、用同一个 tag，消息也不会串。

4. Context 解决的真实 bug：库间消息串扰

没有 context 会怎样：

// 主程序同时用两个第三方库
LibA_compute(MPI_COMM_WORLD, ...);   // 库 A 内部用 tag=5
LibB_compute(MPI_COMM_WORLD, ...);   // 库 B 内部也用 tag=5

库 A 等自己的 tag=5 时，可能误吃掉库 B 的 tag=5 消息。神秘 bug。

修复 —— 给每个库一个独立 communicator：

MPI_Comm comm_A, comm_B;
MPI_Comm_dup(MPI_COMM_WORLD, &comm_A);   // 复制 group，但分新 context_id
MPI_Comm_dup(MPI_COMM_WORLD, &comm_B);   // 再复制一份，又一个新 context_id

LibA_compute(comm_A, ...);
LibB_compute(comm_B, ...);

comm_A 和 comm_B 的 group 一模一样（都是 WORLD 全部进程），但 context_id 不同。MPI 匹配时先看 context_id，库 A 的消息根本进不了库 B 的 Recv 队列。bug 消失。这就是 group 给不了的隔离能力。

5. 完整可跑的例子：用 MPI_Comm_split 创建子 communicator

#include <mpi.h>
int main(int argc, char **argv) {
    MPI_Init(&argc, &argv);

    int world_rank;
    MPI_Comm_rank(MPI_COMM_WORLD, &world_rank);

    // 把进程切成两组：偶数 rank 一组，奇数 rank 一组
    int color = world_rank % 2;        // 0 或 1，同 color 进同一新 comm
    int key   = world_rank;            // 决定新 comm 里的 rank 顺序

    MPI_Comm sub_comm;
    MPI_Comm_split(MPI_COMM_WORLD, color, key, &sub_comm);
    // ↑ collective —— 所有 WORLD 进程都要调用

    int sub_rank;
    MPI_Comm_rank(sub_comm, &sub_rank);
    printf("world %d → sub %d (color=%d)\n", world_rank, sub_rank, color);

    MPI_Comm_free(&sub_comm);
    MPI_Finalize();
}

用 mpirun -n 8 启动后，world_rank=2 在新 communicator 里 rank 变成 1。rank 永远是相对于具体 communicator 的，没有"全局 rank"这种东西。MPI 在内部给 sub_comm 分了一个新的 context_id，保证它和 MPI_COMM_WORLD 的消息互不干扰。

Slide 18 — MPI Communicators and Groups（继续：rank 与子通信器）

这一页用世界地图做例子把上一页的概念落地。MPI_COMM_WORLD 包了全球的进程（P0–P11 散布在地图上），然后又被切成三个子 communicator：MyComm_West、MyComm_Central、MyComm_East，对应美洲 / 非洲 / 亚太。

四个要点

  • A MPI group is an ordered set of processes —— group 是有序集合，不是无序的 set。"有序"意味着每个进程在 group 里的位置是固定的，可以用编号来引用。
  • Each process is associated with an integer rank. Ranks are contiguous and start from zero —— 这就是 MPI 的进程编号系统。N 个进程的 group，rank 就是 0, 1, 2, ..., N-1。从 0 开始、连续、整数这三条要记住，后面所有 MPI 程序的第一行几乎都是 MPI_Comm_rank(MPI_COMM_WORLD, &rank) 来取自己的 rank。
  • A group is used within a communicator to describe the participants in a communication "universe" —— group 描述"谁在场"，communicator 描述"在哪个会议室"。一个进程在不同 communicator 里可能有不同 rank（在世界群是 5 号，在亚太分群是 1 号）。
  • Communicators can be split into sub-communicators —— 这就是地图例子在做的事：把 MPI_COMM_WORLD 切成三个子 communicator。MPI 提供 MPI_Comm_split 函数实现这种切分。常用于"按区域 / 按角色"分组通信，避免无关进程互相打扰。
💡 关键认知：rank 是相对于某个 communicator 的编号。同一个进程在 MPI_COMM_WORLD 和 MyComm_East 里的 rank 通常不同。写代码时要明确"我在哪个 communicator 里说自己是 rank N"。
Communicator 是嵌套关系吗？MPI_Comm_split 会复制进程吗？process 和 rank 又是什么关系？

Process 和 rank 是"对象"和"编号"

不是同一个东西。Process 是 OS 层面的运行实体（"东西本身"）；rank 是这个进程在某个 communicator 里被分配的整数 ID（"编号"）。类比"学生 ↔ 学号"。同一个进程在 WORLD 里 rank=5，在子 communicator 里 rank 可能是 1。所以代码里 MPI_Send 的 dest 写整数，但语义是"在指定 communicator 里编号为 N 的那个进程"。

Communicator 之间没有嵌套关系

每个 communicator 都是独立对象，内部就是一组进程。"sub-communicator"只是俗称（"我从 WORLD 切出来的"），它和 WORLD 在 MPI 里地位平等。不同 communicator 的成员集合可以重叠 —— 同一个进程同时属于多个 communicator 是常态。

MPI_Comm_split 不复制进程，只创建新的 group 标签

8 进程例子：

启动后:
  MPI_COMM_WORLD = {P0..P7}

执行 MPI_Comm_split(WORLD, color, key, &new) 后:
  MPI_COMM_WORLD = {P0..P7}        ← 没动
  MyComm_East    = {P0, P1, P2, P3} ← 新对象（color=0 那组）
  MyComm_West    = {P4, P5, P6, P7} ← 新对象（color=1 那组）

P2 现在同时属于 WORLD 和 MyComm_East。两个 communicator 里 rank 通常不同，所以查 rank 必须明确传 communicator —— MPI_Comm_rank(WORLD, &rw) 和 MPI_Comm_rank(MyComm_East, &re) 返回值不一样。

核心心智模型

Communicator 像"标签"，不像"容器"。一个进程可以贴多个标签。mpirun -n N 之后到 MPI_Finalize 之间，OS 里的进程数量始终是 N，所有 communicator 操作只维护成员关系表，不创建也不销毁进程。

Slide 19 — Point-to-Point and Collective Communication（点对点 与 集合通信）

MPI 的通信操作分两大类：point-to-point（点对点）和 collective（集合）。这一页对比它们。

左栏：Point-to-point（点对点通信，MPI 的基本原语）

The fundamental operation in MPI is point-to-point communication —— 这是 MPI 的"原子操作"。图里 P2 → P5、P3 → P6 各自是一对箭头，代表两次独立的点对点通信。

  • It is simply a matching send/receive pair —— 点对点的本质就是一个 send 配一个 recv。发送方调 MPI_Send(...,dest=5,...)，接收方调 MPI_Recv(...,source=2,...)，两边匹配成功消息才传过去。
  • Think of "point" as a process within a group —— "点"指的是 group 内的一个进程（rank）。
  • The two points must be in the same group —— 发送方和接收方必须在同一个 communicator/group 里。跨组通信要先把它们合并到一个 communicator 里。

右栏：Collective（集合通信，全员参与）

Collective communication involves ALL ranks in a group —— 集合通信的特点是组里的每一个进程都要参与。图里 P0 同时往 P1–P7 发箭头，是典型的 broadcast 模式。

  • Any collective communication can be composed with point-to-point only —— 集合通信在功能上不是必需的，理论上你可以用一堆 send/recv 拼出来一个 broadcast。
  • They exist for convenience and performance reasons —— 但 MPI 仍然提供集合通信原语，因为：(a) 方便 —— 一行代码就能让所有进程同步交换数据；(b) 性能 —— MPI 实现可以用树形 / 分阶段 / 硬件多播等优化算法，比你手写 N 次 send 快得多。
  • Collective primitives are generally expensive —— 但即便优化了，集合通信本身还是贵 —— 因为要等所有进程都到位。一个慢进程拖累全员。

常见的 collective 操作（右下 Examples）

  • Barrier —— 所有进程在此点同步，谁先到谁等。
  • Broadcast —— 一个进程把数据复制给所有其他进程（图里画的就是它）。
  • Reduction —— 把所有进程的数据按某种运算（求和、求最大值等）合并到一个进程。OpenMP 的 reduction 子句就是它的并行版前身。
  • Scan —— 前缀和的并行版本，每个进程拿到的是它和它之前所有进程的累积结果。
💡 设计直觉：能用 collective 就别手写 point-to-point。MPI 实现替你做了优化（树形 reduce、流水线 broadcast 等），手写很难赶上。Point-to-point 留给"少数进程间的不规则通信"。
MPI_Scan / Exscan 实际怎么用？给个具体例子

Scan 就是前缀和的并行版本。每个 rank 持有一个值，集合调用后每个 rank 都拿到一份不同的累积结果。

具体数字例子

调用前（每 rank 持有一个数）:
  Rank 0:  3
  Rank 1:  5
  Rank 2:  2
  Rank 3:  7

执行 MPI_Scan(..., MPI_SUM, ...) 后:
  Rank 0:  3                     (只有自己)
  Rank 1:  3 + 5         = 8
  Rank 2:  3 + 5 + 2     = 10
  Rank 3:  3 + 5 + 2 + 7 = 17

和 Reduce 的区别：Reduce 只让 root 拿到最终值（17）；Scan 让每个 rank 都拿到自己独有的部分和。

Scan 与 Exscan

  • MPI_Scan（inclusive）—— rank i 得到 [0..i] 的累积，含自己。
  • MPI_Exscan（exclusive）—— rank i 得到 [0..i-1] 的累积，不含自己。

实战例子：并行写文件算偏移

每个 rank 有不同数量的数据要写到同一个共享文件：

Rank 0 有 100 个元素   → 起始偏移 0
Rank 1 有 200 个元素   → 起始偏移 100
Rank 2 有  50 个元素   → 起始偏移 300
Rank 3 有  75 个元素   → 起始偏移 350

每个 rank 的偏移 = "在我之前所有 rank 的元素总数"，正好是 MPI_Exscan 的输出。把元素数喂给 Exscan，每个 rank 一次集合调用就拿到自己的写入起点，不需要中央协调。

这是 Scan/Exscan 最经典用途 —— 算偏移、算排名、并行 array compaction（把分布式 boolean 数组里 true 的元素挤到一起）。

Slide 20 — Synchronous and Asynchronous Communication（阻塞 与 非阻塞通信）

这一页讲 MPI 的另一个二分维度：通信调用是阻塞（blocking）还是非阻塞（non-blocking）。这是 MPI 编程里最关键的性能开关之一。

定义对比

  • Blocking：当 API 函数返回时，MPI 保证 message buffer 已经可以安全重用了（对发送方和接收方都是）。换句话说，函数调用要"等通信真做完才返回"。
  • Non-Blocking：API 函数立刻返回，但是不保证通信已经完成。buffer 不安全做读写 —— 可能 MPI 还在后台往里写数据。需要后续配合 MPI_Wait 或 MPI_Test 来确认完成。

关键含义（slide 紫色框）

"Blocking communication means synchronization which results in sequential code!" —— 阻塞通信本质上是同步，会让程序退化成串行执行。

具体来说：

  • A blocked process does not make progress —— 卡在阻塞调用里的进程啥也不能做，CPU 闲置。如果通信慢，等同于浪费算力。
  • Non-blocking communication allows to do work while messages are in flight —— 非阻塞调用启动通信后立即返回，进程可以继续做其他工作（比如算下一批数据），通信和计算并行进行。
  • Most useful property of non-blocking communication is compute-transfer overlap（橙色高亮）—— 这就是非阻塞通信的最终目的：计算和数据传输并行重叠，把通信延迟"藏"在计算时间里。

什么时候选哪个

  • 阻塞 —— 代码简单、易推理。原型阶段、小规模程序、通信不是瓶颈时用。
  • 非阻塞 —— 代码更复杂（要配 MPI_Wait、要小心 buffer 重用），但能藏延迟。性能关键代码、跨节点通信占比大时用。
💡 记住一句话：阻塞 = 安全但闲置；非阻塞 = 高效但要小心 buffer。MPI 程序优化的常见路径就是把热点的阻塞调用改成非阻塞 + 计算重叠。
"Blocking" 到底 block 谁？send 和 recv 的 blocking 保证一样吗？

Block 的范围 = 单个进程内部"这一次调用"

Blocking 不是进程之间的协调机制，而是描述"这一次 MPI 调用什么时候返回"。所以它影响的是同一个进程里"下一行代码什么时候能跑"。

看一段同进程的两行代码：

MPI_Recv(buf, ...);    // (a) 收数据到 buf
compute_using(buf);    // (b) 用 buf 算东西
  • Blocking（MPI_Recv）：(a) 不返回 → (b) 不会执行。等 (b) 跑时 buf 一定已经填好。
  • Non-blocking（MPI_Irecv）：(a) 立刻返回 → (b) 立刻开始跑。但此时数据可能还在路上，(b) 读到的是垃圾。

所以"non-blocking 时 buffer 不安全"的根本原因是：MPI 库在后台往 buf 里写，你的代码同时在读 buf —— 经典的边读边写。必须用 MPI_Wait 等 MPI 写完再访问。

Send 和 Recv 的 blocking 保证不同，要分清

调用Blocking 返回时保证什么
MPI_Recvbuffer 已经填好，可以直接用数据
MPI_Sendsend buffer 可以重用了（不保证对方已收到 —— 可能还在 MPI 内部 buffer 里）

这点很容易误解：blocking MPI_Send 返回 不等于"对方收到了"。它只表示"你修改这个 buffer 不会破坏正在发送的数据"。"对方是否收到"在 standard mode 下是看 MPI 实现的（见 slide 34）。

Compute-transfer overlap 的标准代码骨架

要把通信延迟藏到计算里，标准三步走：

MPI_Request req;
MPI_Isend(prev_results, ..., &req);   // (1) 启动发送，立刻返回

compute(next_batch);                  // (2) 和发送并行进行 ←关键

MPI_Wait(&req, MPI_STATUS_IGNORE);    // (3) 等发送完，prev_results 才能再用

整体耗时近似 max(通信, 计算)，而不是 通信 + 计算。如果用 blocking MPI_Send，CPU 在通信期间完全闲置，时间就退化成两者之和。

使用约束：(1) 和 (3) 之间，prev_results 这个 buffer 不能改、不能再用，只有 (3) 之后才安全。next_batch 必须是独立的另一块 buffer，否则违反这个约束。

💡 两条记忆：(1) blocking 解决的问题 = "我下一行代码能不能安全用/改这个 buffer"；(2) non-blocking 解决的问题 = "通信跑着的时候 CPU 别闲着"。

Slide 21 — Anatomy of an MPI Message（一条 MPI 消息长什么样）

这一页把"一条 MPI 消息"拆开看，里面有两部分：envelope（信封，元数据）和 body（信体，实际数据）。这是后面 MPI_Send/MPI_Recv 参数顺序的来源 —— 看懂这一页参数表就不用死记硬背了。

Envelope（元数据，固定大小）

信封负责"路由"，决定消息从谁发到谁、归哪类。共四个字段：

  • source / destination —— 发送方和接收方的 rank。
  • communicator —— 这次通信发生在哪个 communicator 内（描述通信上下文）。
  • tag —— 一个整数标签，接收方可以用它在多种消息里挑出"我想收的那种"。比如同一对进程之间可以同时跑"梯度消息（tag=1）"和"控制信号（tag=2）"，互不混淆。

Body（实际数据，大小可变）

  • count —— 消息里有多少个元素。不是字节数，是元素个数。这是新手常踩的坑。
  • datatype —— 单个元素的类型（如 MPI_INT、MPI_DOUBLE）。MPI 用 datatype + count 自己算字节数，所以你不用算。
  • buffer —— 数据起始地址。也就是 C/C++ 里你要发的那个数组的首指针。

对照例子（slide 下方的代码）

if (Process_A) {
    MPI_Send(send_buffer, count, datatype, destination, tag, MPI_COMM_WORLD);
} else if (Process_B) {
    MPI_Recv(recv_buffer, count, datatype, source, tag, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
}

对应关系一目了然：前三个参数是 body（buffer / count / datatype），后三个是 envelope（dest 或 source / tag / communicator）。MPI_Recv 末尾多一个 status，用来查接收到的真实元数据，不需要时填 MPI_STATUS_IGNORE。

💡 记忆口诀：参数顺序 = "body 三件套 + envelope 三件套"。Send 的 envelope 写"对方"，Recv 的 envelope 写"对方 + status"。count 永远是元素数不是字节数。
Communicator 的 context 到底是什么？同一个 group 能创建多个 communicator 吗？

Context = MPI 内部维护的"隔离命名空间"

每个 communicator 创建时，MPI 给它分配一个独立的隐形 ID（context）。这个 ID 不可见、查不到，但 MPI 用它保证不同 communicator 上的消息绝对不会跨域匹配，即使 source / dest / tag 都一致。

Context 是空间维度的隔离层，不是时间维度的"历史"。

为什么需要这种隔离

典型场景：第三方库。设想你的应用里用了某个 MPI 写的 FFT 库。库内部也发消息，可能也用 MPI_COMM_WORLD、tag=5。如果你的应用代码恰好也在 WORLD 上发 tag=5，两边消息会合法地互相匹配 —— 行为彻底错乱。

正规库的做法：初始化时复制一份属于自己的 communicator：

MPI_Comm lib_comm;
MPI_Comm_dup(MPI_COMM_WORLD, &lib_comm);   // 成员同 WORLD，context 不同

之后库内部所有通信都用 lib_comm。即使 source/dest/tag 与应用一致，两边永远不会跨匹配。

同一个 group 可以有多个 communicator

MPI_Comm_dup 就是干这个的：复制成员列表，分配新的 context。可以重复多次，得到任意多个"成员相同、context 不同"的 communicator。库设计的标准模式 —— 每个独立模块各拿一个，互不干扰。

Context 的粒度：communicator 级

同一个 communicator 上发出的所有消息共享这个 communicator 的 context ID。它是 communicator 的属性，不是单条消息的属性。完整的消息匹配规则：

context 一致     ← 由 communicator 决定
source/dest 一致
tag 一致 (或 ANY_*)

Context 提供"粗粒度的隔离"，source/dest/tag 提供"细粒度的挑选"。

直观比喻

Communicator 像 Slack workspace：每个 workspace 有独立的内部 ID（= context）；同一群人可以加入多个 workspace（= 多次 dup 同一个 group）；在 workspace A 里 @某人，消息绝对不会跑到 workspace B —— 即使两个 workspace 成员完全一样、tag 完全一样。

对用户不可见

MPI 不提供查 context ID 的 API。它纯粹是 MPI 内部簿记，用 communicator 句柄作代理。这就是为什么 API 里只传 communicator、不传 context —— 后者隐含在前者里。

Slide 22 — General MPI Program Structure（MPI 程序的整体骨架）

这一页给出每个 MPI 程序都长得很像的"骨架代码"：#include <mpi.h> → MPI_Init → 干活 → MPI_Finalize。

骨架的三段结构

#include <mpi.h>
int main(int argc, char *argv[]) {
    // (1) Serial code begin —— 这里还是串行

    MPI_Init(&argc, &argv);    // (2) parallel code begin
    // ... do work and MPI calls here ...
    MPI_Finalize();             // parallel code end

    // (3) Serial code end —— 这里又回到串行
    return 0;
}

关键是中间这段才是"MPI 并行段"。MPI_Init 之前和 MPI_Finalize 之后都是串行代码，不能调用任何 MPI 函数。

slide 列出的硬规则

  • 必须先 init 再 finalize —— 两端配对，少一个就出错。
  • MPI 调用只能在 init 和 finalize 之间 —— 之前/之后调用 MPI 函数行为未定义。
  • 在 init 之前和 finalize 之后是串行代码 —— 这两段任何 MPI 操作都不可用。
  • 必须 #include <mpi.h> —— 才能用 MPI 库的声明。
  • 所有 MPI 函数名以 MPI_ 开头（profiling 接口用 PMPI_），C/C++ 大小写敏感，Fortran 不敏感。

紫色框里那条"反向规则"

"Your code must not declare variables or functions that begin with MPI_ or PMPI_" —— 你自己定义的变量/函数不能以 MPI_ 或 PMPI_ 开头。这两个命名空间被 MPI 标准独占，你的 MPI_my_var 可能和未来某个 MPI 实现的内部符号冲突，导致莫名链接错误。

💡 本页就一句话：MPI 程序就是"三明治结构 —— 串行 / Init...Finalize 并行 / 串行"，在并行段里写所有 MPI 调用。命名空间 MPI_/PMPI_ 自己别用。
为什么 MPI_Init(&argc, &argv) 要传命令行参数？

历史遗留 + 可选机制。早期 MPI 实现里，mpirun/mpiexec 启动进程时会把自己的参数（守护进程地址、rank 信息等）注入到 argv 里。MPI_Init 拿到 &argc, &argv 后会就地读取并剔除这些"内部参数"，让用户后续解析命令行时只看到自己关心的那些。用指针就是为了支持 in-place 修改数组长度和内容。

MPI-2 之后传 NULL, NULL 也合法 —— 现代实现基本走环境变量传递信息，已经不依赖命令行注入。但 API 签名为了向后兼容保留下来，写 MPI_Init(&argc, &argv) 是约定写法，传不传 NULL 实际行为几乎没差别。

Profiling 接口（PMPI_）是什么？

MPI 标准为每一个 MPI 函数都同时定义了两个入口名：MPI_Xxx（用户调用）和 PMPI_Xxx（同一个函数的"真身"，加 P 前缀）。目的是让性能分析工具能拦截所有 MPI 调用而不需要改用户代码。

机制：profiling 库重新定义 MPI_Send，里面记录时间/字节数后再调 PMPI_Send 走真实通信。用户代码只需要重链接，不用改一行源码就能开关 profiling。

// profiling 库里的 wrapper：
int MPI_Send(const void *buf, int count, MPI_Datatype dt,
             int dest, int tag, MPI_Comm comm) {
    double t0 = MPI_Wtime();
    int rc = PMPI_Send(buf, count, dt, dest, tag, comm);
    double t1 = MPI_Wtime();
    log_send(dest, count, t1 - t0);
    return rc;
}

mpiP、Vampir、Scalasca、TAU 这些工具都是基于 PMPI 接口实现的。这就是为什么用户代码不能定义以 MPI_/PMPI_ 开头的符号 —— 这两个命名空间被标准独占用作用户层和"真身"层的入口。

Slide 23 — Hello MPI（第一个 MPI 程序：编译与运行）

这一页是 MPI 的"Hello World"，重点是从源码到运行的一整套工具链：编译用什么、启动用什么、在 SLURM 集群上又怎么改。

源码（左上）

#include <iostream>
#include <mpi.h>
int main(int argc, char *argv[]) {
    MPI_Init(&argc, &argv);
    std::cout << "Hello MPI\n";
    MPI_Finalize();
    return 0;
}

就是骨架 + 一行 cout。每个进程都会执行这条 cout，所以 -n 2 启动会打两次。

编译：mpic++（compiler wrapper）

mpic++ 是 MPI 提供的编译器包装器，本质上还是调用 g++，但它替你把 MPI 的头文件路径（-I/...）和库链接（-lmpi）都加上了。slide 用 mpic++ -show 命令证明这一点 —— 输出会展示它实际跑的 g++ 命令很长。日常使用：

mpic++ -o hello_mpi hello_mpi.cpp

用法和 g++ 完全一样，所以从普通 C++ 项目迁移很无痛。

运行：mpirun（runtime wrapper）

mpirun -n 2 ./hello_mpi —— -n 2 让 MPI 启动 2 个进程副本。每个副本都是同一个 ./hello_mpi，但每个进程的 rank 不同（这就是 SPMD：Single Program, Multiple Data）。输出 "Hello MPI" 会打两次。

用 ps | grep hello_mpi 可以看到确实有两个进程在跑。

在 SLURM 集群上：用 srun 替代 mpirun

HPC 集群通常用 SLURM 调度作业。这时候启动 MPI 程序用 srun：

srun -n 2 -c 1 ./hello_mpi
  • -n 2（即 --ntasks=2）—— 申请 2 个 task，对应 2 个 MPI 进程。
  • -c 1（即 --cpus-per-task=1）—— 每个 task 用 1 个 CPU 核心。如果你的程序还混了 OpenMP，可以把这个调高，让每个 MPI 进程内部多线程。

语义和 mpirun -n 2 一致，但 srun 让 SLURM 接管资源分配，所以会按你的作业脚本里申请的节点和 CPU 走。

💡 三件套要分清：mpic++ 编译，mpirun 启动（本机），srun 启动（SLURM 集群）。-n N 决定起几个进程；同一份代码每个进程都跑一遍，靠 rank 区分。
-pthread 编译选项是什么？为什么 mpic++ -show 里会出现？

-pthread 是 GCC/Clang 的编译+链接 flag，做三件事：(1) 链接 libpthread；(2) 定义 _REENTRANT 宏，让标准库走线程安全版本（如 errno 变成 per-thread）；(3) 设置编译器里线程相关的代码生成选项。

它出现在 mpic++ -show 输出里，不是因为用户程序要多线程，而是因为 MPI 库本身用 pthread 实现内部功能（异步通信进度推进、RMA 推进、某些 I/O 后台线程等）。链接 MPI 库的程序必须带 -pthread 才能解析这些符号，所以纯 MPI 单线程程序也会看到这个 flag。

-pthread vs -lpthread：后者只链接库不做其他事，是过时写法；现代用法都用 -pthread。

SLURM 里的 task、node、-c 和 MPI 进程的对应关系？

SLURM 的 task 是个通用资源单位，含义是"启动一份程序的实例"。SLURM 自己不知道这份实例里跑什么，只负责按 -n 指定的数量去启动。对 MPI 程序，1 task = 1 MPI 进程 = 1 rank。

选项控制什么对应 MPI 概念
-N (--nodes)物理节点数程序分布在几台机器上
-n (--ntasks)进程总数MPI 进程总数（= 总 rank 数）
-c (--cpus-per-task)每个进程预留的 core 数MPI 进程内 OpenMP 线程数上限

-N 和 -n 是独立的旋钮：-N 1 -n 4 是单节点跑 4 进程，-N 4 -n 4 是 4 节点各跑 1 进程，-N 2 -n 8 是 2 节点每节点 4 进程。

-c 的真正用途是给一个 task 预留多个 core 让它内部开多线程，最典型场景是 MPI + OpenMP 混合并行 —— 每个 MPI 进程独占多个 core 跑 OpenMP 线程。如果不指定，默认每个 task 1 个 core，你 OpenMP 开多线程会全挤在一个 core 上互相抢，性能反而崩。

MPI 进程能在同一个 node 上跑吗？同节点的进程怎么通信？

能，而且单节点多 MPI 进程是常态。现代 node 一般有 64-128 个 core，1 节点 1 进程会浪费绝大多数算力。实际部署有两种主流模式：

  • 纯 MPI：每 core 一个 MPI 进程，单节点上同时存在几十上百个 ranks。
  • MPI + OpenMP 混合：每 socket 一个 MPI 进程，进程内开 OpenMP 线程吃满 socket。

MPI 的"分布式"指的是内存模型，不是物理位置。模型层规定每个进程独立地址空间、必须显式 send/recv 通信；物理层进程在哪、隔多远、怎么连，都不影响代码正确性。用户代码 MPI_Send 的写法跨节点和同节点完全一致。

同节点通信底层走共享内存，不走网络。MPI 库会自动检测两个 rank 是不是在同一台机器，挑最快的传输方式：

通信场景底层用什么延迟量级
跨节点InfiniBand / Ethernetμs–ms
同节点跨 socket共享内存（POSIX shm / CMA / XPMEM）0.1–1 μs
同 socketL3 cache + 共享内存<0.1 μs

用户代码完全不感知传输方式的切换 —— 这是 MPI 抽象的核心威力：同一份代码，跨节点能跑，单节点也能跑。

同节点的 core 不是物理共享 RAM 吗？为什么 MPI 进程之间还隔离？

关键区分：物理 RAM 共享 ≠ 进程地址空间共享。同 node 上所有 core 物理上确实共享同一块 RAM 和 L3 cache —— 这是硬件事实。但 OS 给每个 process 维护独立的 page table（虚拟地址 → 物理地址的映射），主动强制隔离它们的地址空间：Process A 的 page table 里根本没有指向 Process B 物理页的条目，所以 A 不管怎么折腾自己的指针，MMU 硬件都不会把它解析到 B 的物理页。

单位共享物理 RAM共享虚拟地址空间能直接读对方变量
同进程内多 thread✓✓✓
同节点多 process✓✗✗
跨节点多 process✗✗✗

所以 thread 能直接读共享变量、process 不能 —— 原因不是物理内存隔离，而是 OS 在 page table 上主动隔离。MPI 选 process 这种隔离单位，正是为了让"同节点"和"跨节点"在编程模型上完全统一。

MPI 同节点 shm 通信的实际机制：双方主动调 shm_open/mmap，让 OS 把同一物理页同时挂进两份 page table，形成一块"共享窗口"作为消息缓冲区。普通变量仍然各自隔离，只有这扇用户看不见的窗口是共享的。

为什么集群上能直接用 srun 启动 MPI 程序，不用 mpirun？

因为 srun 是 SLURM 自带的启动器，通过 PMI/PMIx 协议直接和 MPI 库握手，可以跳过 mpirun 这一层。

集群上的 MPI 库（OpenMPI / MPICH / Intel MPI）通常编译进了 PMI/PMIx 客户端，srun 内置 PMI/PMIx 服务端。启动流程：

  1. srun -n 4 a.out 在 SLURM 已分配的节点上启动 4 个 a.out。
  2. 每个 a.out 调 MPI_Init。
  3. MPI_Init 通过环境变量发现 srun 提供的 PMI 服务，连过去问"我是谁？其他 rank 在哪？"。
  4. PMI 服务端把 rank 编号、网络地址等信息发回，进程间握手，通信通道建立。

为什么集群推荐 srun 而不是 mpirun：

  • 资源记账准确：srun 启动的进程都在 SLURM 视野里，CPU 时间和内存正确记账；mpirun 自己 fork 可能绕过 SLURM 的 cgroup 限制。
  • 绑核正确：srun 知道 SLURM 分配了哪些具体 core，按 --cpu-bind 钉得准。
  • 启动更快：少一层 mpirun 进程。
  • 管理统一：scancel、squeue、sacct 对 SLURM 启动的进程才完整有效。

一句话：集群上 SLURM 是统一入口，srun 既负责资源管理又负责 MPI 进程启动 —— mpirun 那层在集群环境里是多余的。

Process 会和 CPU core 一对一绑定吗？还是像线程一样多个共用一个 core 排队？

OS 调度层面，process 和 thread 都是 task_struct，调度器一视同仁。一个 core 在某一时刻只能跑一份指令流，靠时间片轮转让多个 task "看起来同时在跑"。所以 process 默认不绑死在某个 core，OS 调度器可以自由把它从 core 0 迁到 core 5。"一个 core 处理多个进程，他们排队"这个理解是对的，是 OS 默认行为。

但 HPC / MPI 场景主动绑核（CPU affinity / pinning）几乎是标配，理由：

  • 缓存局部性：进程被迁到新 core 后，老 core 的 L1/L2 cache 全失效，要重新拉数据。
  • NUMA 亲和性：进程在 socket A 分配的内存被迁到 socket B 的 core 上跑，每次访存都要跨 socket，慢一档（详见下一题）。
  • 可重复性：性能测量场景不希望调度器随机迁移影响结果。

绑核机制：srun --cpu-bind=cores / Linux 系统调用 sched_setaffinity / taskset。绑核之后进程只能在指定 core 上调度。

注意：绑核 ≠ 独占。绑核只限制"自己的进程不能离开指定 core"，但其他进程（系统服务、cron job）仍可能被调度到同一个 core 上来抢时间片。真要独占整段 core，得靠 SLURM 的 cgroup + cpuset 整节点隔离。

SMT (Hyperthreading)：现代 CPU 一个物理 core 通常带 2 个硬件线程上下文，OS 看到的逻辑 core 数 = 物理 core × 2。同一物理 core 的两个 SMT 上下文同时跑两份 task 时不是排队，是真并发，但共享 L1/L2 和执行单元会互相干扰。HPC 一般关掉 SMT 或只用一半逻辑 core。

Socket 是什么？和 L1/L2/L3 cache 是什么关系？

Socket = 主板上的物理 CPU 插槽，每个 socket 装一颗 CPU 芯片（package）。"双 socket 服务器"就是主板上两个插槽各装一颗 CPU。Cache 长在 CPU 芯片内部，所以 cache 的"作用域"被 socket 这条物理边界划分。

典型双 socket 服务器（每 socket 8 core）的拓扑：

┌──────────────────────────────────────────────────────────┐
│  Socket 0 (一颗 CPU)                                     │
│  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬─────┐│
│  │Core 0│Core 1│Core 2│Core 3│Core 4│Core 5│Core 6│Core7││
│  │L1+L2 │L1+L2 │L1+L2 │L1+L2 │L1+L2 │L1+L2 │L1+L2 │L1+L2││ ← L1/L2 每 core 独占
│  └──────┴──────┴──────┴──────┴──────┴──────┴──────┴─────┘│
│  ┌──────────────────────────────────────────────────────┐│
│  │       L3 cache (8 个 core 共享，~32 MB)              ││ ← L3 socket 内共享
│  └──────────────────────────────────────────────────────┘│
│  ┌──────────────────────────────────────────────────────┐│
│  │  Memory Controller → Local DRAM (~128 GB)            ││ ← 本 socket 的近内存
│  └──────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────┘
                         ↕  UPI / Infinity Fabric (插槽间互连)
┌──────────────────────────────────────────────────────────┐
│  Socket 1 (另一颗 CPU，结构对称，独立的 L3 和 DRAM)      │
└──────────────────────────────────────────────────────────┘

Cache 归属规则：

层级归属典型大小延迟
L1 (data + instruction)每个 core 独占32-64 KB / core~1 ns
L2每个 core 独占（或每对 core 共享）256 KB - 2 MB / core~3-10 ns
L3 (LLC)同 socket 内所有 core 共享16-100 MB / socket~10-40 ns
DRAM (本 socket)同 socket 内 core 共享几十-几百 GB~80-100 ns
DRAM (远 socket)跨 UPI 访问—~150-300 ns

关键三点：

  • L3 是 socket 边界：跨 socket 不共享 L3，要走 UPI/Infinity Fabric 互连。
  • DRAM 按 socket 分区（NUMA）：每颗 CPU 自带内存控制器接一组 DIMM。访问本 socket 的 DRAM 比邻居 socket 的快。
  • L1/L2 是 core 私有：同 socket 内不同 core 想同步数据也得经 L3 或 cache coherence 协议（MESI）。

这就是为什么 MPI + OpenMP 混合并行的最佳实践是"每 socket 一个 MPI 进程"：进程内的 OpenMP 线程共享这个 socket 的 L3 和本地 DRAM，跨 socket 才走 MPI 显式消息 —— 让每个进程的工作集尽量留在自己 socket 的 cache + NUMA 域里。

Slide 24 — MPI Environment Management Routines（MPI 环境管理函数）

这一页是"必须认识的 7 个 MPI 函数"清单。它们不参与通信本身，但每个 MPI 程序都会用到。

初始化与终止

  • MPI_Init / MPI_Init_thread —— 启动 MPI 运行环境。每个 MPI 程序里必须调一次，且只能一次，必须在所有其他 MPI 函数之前。如果程序还要多线程，用 MPI_Init_thread 来声明所需的线程支持级别（详见 slide 26）。
  • MPI_Finalize —— 终止 MPI 环境。必须是最后一个 MPI 调用，之后任何 MPI 函数都不能再调。
  • MPI_Abort —— 紧急刹车：终止某个 communicator 上的所有进程。多数实现里它直接终止整个程序的所有进程，无视你传的 communicator。出错时强制退出常用它。

查询身份与规模

  • MPI_Comm_size(comm, &size) —— 查给定 communicator 里总共有多少个进程。例如 MPI_Comm_size(MPI_COMM_WORLD, &size) 返回 mpirun -n N 里的 N。
  • MPI_Comm_rank(comm, &rank) —— 查"我"在这个 communicator 里的 rank。每个进程独立调，得到的值不同，从 0 到 size-1。这是写 SPMD 代码区分进程的关键 —— "if (rank == 0) ... else ..."。

其他工具函数

  • MPI_Wtime() —— 返回 wall clock 时间（秒，double 精度）。差两次调用得到代码段执行时间，是 MPI 程序里测性能的标准做法。
  • MPI_Get_version —— 查当前链接的 MPI 实现到底实现的是 MPI 标准的哪个版本/子版本（比如 3.1、4.0）。
💡 最常用 4 个：MPI_Init / MPI_Finalize 一对，MPI_Comm_size / MPI_Comm_rank 一对。会这四个就能写大部分入门 MPI 代码。其他 3 个（Abort/Wtime/Get_version）按需查。
MPI_Comm_size 的值会受绑核或硬件 core 数影响吗？

不会。进程数完全由启动器的 -n 参数决定，跟绑核、硬件 core 数、调度策略都无关。MPI_Init 时通过 PMI/PMIx 从启动器拿到 N，直接写进 MPI_COMM_WORLD。后续怎么调度只影响进程在哪个 core 上跑，不影响进程数量。

场景-n硬件 coreMPI_Comm_size
单核机器跑 mpirun -n 4414（4 进程时间片轮转共用 1 core）
64 核服务器跑 mpirun -n 22642（其余 62 个 core 闲着）
mpirun -n 8 在 4 核机器上848（每 core 分时跑 2 进程）

所以 slide 上"MPI_Comm_size(MPI_COMM_WORLD, &size) 返回 mpirun -n N 里的 N"是无条件成立的事实查询。

一个进程能同时用多个 core 吗？跨 core 共享数据要付什么代价？

单线程进程：任意瞬间只用一个 core（OS 可以迁移它，但一个时刻一个 core）。

多线程进程：可以同时占多个 core。线程是独立的调度单位（独立 task_struct），N 个线程可以被分配到 N 个 core 上并行执行，共享进程的地址空间。MPI + OpenMP 就吃这个机制 —— srun -n 4 -c 8 给每个 MPI 进程分 8 个 core，进程内开 8 个 OpenMP 线程并行跑。

跨 core 共享数据有代价 —— 但不是用户层 copy-paste，是硬件自动做的 cache coherence (MESI 协议)。机制叫 cache line ping-pong：

Core 0 写 X = 5
  → MESI 广播 invalidate 给 Core 1
  → Core 1 的 L1 副本作废
  → Core 0 副本变 Modified           (~30 ns)

Core 1 想读 X
  → L1 已作废，未命中
  → 协议把 Core 0 的副本经 L3 转给 Core 1   (~30-50 ns)

同一条 cache line 在两个 core 之间反复传递就是 ping-pong，会成为性能瓶颈。

False sharing（假共享）：两个线程改的是不同变量，但变量恰好落在同一条 cache line（cache line 通常 64 字节）。逻辑上无冲突，硬件却照样 ping-pong —— 代码看起来无锁，性能比单线程还慢。修复：用 alignas(64) 或 padding 把变量分到不同 cache line。

代价分级（这是 MPI + OpenMP 设计的核心依据）：

共享方式延迟量级触发场景
同 core L1 命中~1 ns局部变量
同 socket L3 / coherence~30-50 nsOpenMP 线程跨 core 共享
跨 socket UPI 协调~150-300 ns跨 socket 共享数据
同节点 MPI 消息 (shm)~1 μsMPI ranks 跨进程通信
跨节点 MPI 消息 (网络)~5-100 μsMPI ranks 跨节点通信

为什么"每 socket 一个 MPI 进程 + 进程内开 OpenMP 线程"是甜蜜点：socket 内用 OpenMP 共享 L3（~50 ns），socket 外用 MPI 显式消息（~1 μs）。把"低成本共享"留给硬件 coherence，把"高成本通信"用程序员可控的 MPI 显式管 —— 每一档代价对应最匹配的工具。

Slide 25 — Print Hostname with MPI（打印每个进程跑在哪台机器上）

这一页是 example-2，比 Hello MPI 进一步 —— 让每个进程报告自己的 rank、总进程数、所在主机名。完整地用上了 slide 24 的几个环境管理函数。

关键代码片段

int rank, size, len;
char hostname[MPI_MAX_PROCESSOR_NAME];

MPI_Init(&argc, &argv);
err = MPI_Comm_size(MPI_COMM_WORLD, &size);  assert(err == MPI_SUCCESS);
err = MPI_Comm_rank(MPI_COMM_WORLD, &rank);  assert(err == MPI_SUCCESS);
err = MPI_Get_processor_name(hostname, &len); assert(err == MPI_SUCCESS);

std::cout << "Rank " << rank << "/" << size
          << " running on: " << hostname << "\n";
MPI_Finalize();

新出现的两个 API

  • MPI_Get_processor_name(buf, &len) —— 把当前进程所在节点的主机名写入 buf，长度写入 len。debug "我跑在哪台机器上"时常用。MPI_MAX_PROCESSOR_NAME 是标准定义的最大长度常量，分配数组用它最稳。
  • 错误码检查 —— 注意每个 MPI 调用都用 err 接返回值，再 assert(err == MPI_SUCCESS)。slide 强调：几乎所有 MPI 函数都返回错误码，建议检查，但实际工程里常被省略。MPI_SUCCESS 是成功返回的标准常量。

运行输出

$ mpirun -n 4 ./rank_size_proc
Rank 0/4 running on: platus
Rank 3/4 running on: platus
Rank 1/4 running on: platus
Rank 2/4 running on: platus

4 个进程都跑在同一台机器（platus）上，因为只是本地测试。

输出顺序为什么是乱的

slide 最后一条 bullet 点出来："Similar to shared memory, the order of the output from each process is arbitrary" —— 跟 OpenMP 多线程一样，多进程同时往 stdout 写，谁先 flush 谁先出现，OS 不保证 rank 顺序。要排序输出只能让 rank 0 收齐再打印（用通信汇总）。

💡 两条工程习惯：(1) MPI_Get_processor_name + rank 是 debug 分布式 bug 时的好朋友，能立刻看出"哪个节点上的哪个进程"出问题；(2) MPI 输出顺序不可控，别假设它按 rank 来。

Slide 26 — MPI with Thread Support（MPI + 多线程的兼容级别）

这一页讲当 MPI 进程内部还要开多线程（MPI + OpenMP / pthread）时怎么处理。MPI 不是默认就线程安全的，必须明确声明你打算怎么用线程。这就是 MPI_Init_thread 和它的"四个级别"的存在原因。

用 MPI_Init_thread 替代 MPI_Init

调用形式：

int required = MPI_THREAD_FUNNELED;  // 你期望的级别
int provided;
MPI_Init_thread(&argc, &argv, required, &provided);

你提"我想要这种线程支持"，MPI 实现告诉你"我能给的是哪种"。provided 不一定等于 required —— 实现可能给得比你要的低（不够用）或高（够用）。所以拿到 provided 后通常要检查是否满足需求。

四个级别（从严到松）

  • MPI_THREAD_SINGLE —— 进程里只有一个线程。最简单，等同于不启用线程支持。
  • MPI_THREAD_FUNNELED —— 进程可以多线程，但只有调用了 MPI_Init_thread 的那一个线程（通常是主线程）能调 MPI 函数。其他线程只能算它们自己的活。这是最常见的"MPI + OpenMP"模式：主线程做 MPI 通信，其他 OpenMP 线程并行算。
  • MPI_THREAD_SERIALIZED —— 多线程都可以调 MPI，但同一时刻只能有一个 在调（你需要自己加锁/同步保证）。
  • MPI_THREAD_MULTIPLE —— 完全自由，多个线程可以同时调用 MPI，无任何限制。最灵活，但实现起来最重，不是所有 MPI 实现都对它支持得很好。

例子里输出的整数值

slide 输出框里：

MPI_THREAD_SINGLE: 0
MPI_THREAD_FUNNELED: 1
MPI_THREAD_SERIALIZED: 2
MPI_THREAD_MULTIPLE: 3

这四个常量在 MPI 头文件里就是 0/1/2/3，所以 "provided >= required" 这种比较是合法的，可以直接判断"实际给的级别够不够"。例如要求 SERIALIZED（2），实际拿到 MULTIPLE（3）也是 OK 的。

💡 实战选择：纯 MPI 用 MPI_Init 就行。混合 MPI+OpenMP 一般用 MPI_THREAD_FUNNELED（最常见、最稳）。需要多线程同时通信再升 SERIALIZED/MULTIPLE，但要确认实现真的支持。
Funneled 是什么意思？给出三档（FUNNELED/SERIALIZED/MULTIPLE）的工作代码示例

Funnel = 漏斗。FUNNELED 的语义是：进程内可以多线程，但所有 MPI 调用必须从一个固定的"窄口" —— primary 线程 —— 过去。线程团队的活最后通信这一步要被"漏到"主线程上。

FUNNELED：经典 MPI + OpenMP fork-join

MPI_Init_thread(&argc, &argv, MPI_THREAD_FUNNELED, &provided);

double local_sum = 0.0;
#pragma omp parallel for reduction(+:local_sum)
for (int i = 0; i < N; i++) {
    local_sum += heavy_compute(i);   // 并行区不调 MPI
}
// 出 parallel 区，只剩 master thread 在跑

double global_sum;
MPI_Reduce(&local_sum, &global_sum, 1, MPI_DOUBLE,
           MPI_SUM, 0, MPI_COMM_WORLD);   // 只 master 调 MPI

结构上保证"只 primary 调 MPI"，不需要锁。

SERIALIZED：任何线程都能调，但用户加锁串行

MPI_Init_thread(&argc, &argv, MPI_THREAD_SERIALIZED, &provided);

#pragma omp parallel
{
    int tid = omp_get_thread_num();
    double partial = compute_partial(tid);

    #pragma omp critical
    {
        MPI_Send(&partial, 1, MPI_DOUBLE,
                 0, tid, MPI_COMM_WORLD);
    }
}

每线程发自己的数据，省去了汇总到 master 的中间步骤；但 critical 强制串行，用户必须自己保证一次只一个线程进 MPI。

MULTIPLE：多线程真并发调 MPI

MPI_Init_thread(&argc, &argv, MPI_THREAD_MULTIPLE, &provided);
if (provided < MPI_THREAD_MULTIPLE) MPI_Abort(MPI_COMM_WORLD, 1);

#pragma omp parallel
{
    int tid = omp_get_thread_num();
    double partial = compute_partial(tid);
    // 没 critical，多线程同时进入 MPI 库
    MPI_Send(&partial, 1, MPI_DOUBLE,
             0, tid, MPI_COMM_WORLD);
}

用户不需要任何同步，库内部自己加锁。开销最高，但部分实现/网卡支持下能吃满硬件多通道。

这四个级别真正约束的是什么？MPI 通信会冲突吗？

关键拆分两层独立的并发：

层次并发参与者是否有冲突风险由谁解决
进程间不同 ranks 的 primary thread永远不冲突MPI 协议本身（消息匹配引擎）
进程内同 process 的多个 thread可能冲突线程支持级别契约

进程间永远不冲突的原因：每个 process 只读写自己私有内存。MPI_Send 是从自己的 send_buf 读数据交给库；MPI_Recv 是让库往自己的 recv_buf 写数据。两个 process 的内存是隔离的，根本没有"两个 process 同时写一份内存"这种情况。多个 send 同时到达接收方时，库的消息匹配引擎按 envelope (source, tag, comm) 配对，每条 Send 恰好被一次 Recv 消费，FIFO 保证（同一对 sender→receiver 的消息不会乱序）。

进程内可能冲突的原因：MPI 库内部的数据结构（消息队列、待匹配请求列表、网络缓冲区状态）在一个 process 里是单一实例，多个 thread 同时改它们就是经典 race。线程级别契约就是为了管这件事。

"谁能调"和"能否真并发"是两个独立维度，注意 SERIALIZED 不是允许并发，而是"谁都能调但仍然 1 次 1 个"：

级别谁能调同时刻 MPI 调用数
FUNNELED只 primary1（结构上保证）
SERIALIZED任何线程1（用户加锁保证）
MULTIPLE任何线程多个（库内部加锁保证）

SERIALIZED 相对 FUNNELED 的真正收益是代码结构：每线程直接发自己的数据，省去汇总到 master 的中间步骤；但同时刻 MPI 调用数仍是 1，性能上限和 FUNNELED 一样。要真正多个 MPI 同时进行，必须 MULTIPLE。

单 process 怎么达到"同时和多个 peer 通信"？

有两个独立的并发维度，可以单独用也可以组合用：

单线程多线程 (MULTIPLE)
Blocking MPI同时 1 个调用同时 N 个调用（N 线程各自阻塞）
Non-blocking MPI同时多个 in-flight同时 N × M 个 in-flight

维度 1：non-blocking 调用（单线程就能做到）

MPI_Request reqs[3];
MPI_Isend(buf1, ..., dest=1, ..., &reqs[0]);   // 立即返回
MPI_Isend(buf2, ..., dest=2, ..., &reqs[1]);   // 立即返回
MPI_Isend(buf3, ..., dest=3, ..., &reqs[2]);   // 立即返回
// 三个 send 同时在路上飞
do_other_compute();
MPI_Waitall(3, reqs, MPI_STATUSES_IGNORE);

Isend/Irecv 把"启动通信"和"等待完成"分离，函数立即返回 request 句柄，真正搬运由库后台进行。一个线程能同时维持任意多个 in-flight 操作。Collective（Bcast/Allreduce/Alltoall）一次调用底下也是触发多对多并发传输，但用户只见一个 API。

维度 2：多线程并发 MPI（仅 MULTIPLE）

FUNNELED/SERIALIZED 同时刻只有 1 个 MPI 调用；MULTIPLE 下多个线程才真的并发进入 MPI 库。

实战常见组合：FUNNELED + 主线程内大量 non-blocking 调用 —— 既保证 MPI 库零锁开销，又通过 non-blocking 达到计算-通信重叠和多 peer 并发。MULTIPLE 只在每线程对接独立的网络流（如每线程一个 GPU stream）时才有额外收益。

硬件层是否真并行：

  • 同节点（shm）：每对 (sender, receiver) 走自己的 ring buffer，多对并发几乎线性扩展。
  • 跨节点：现代 InfiniBand/RoCE 网卡有多 QP（Queue Pair）队列，可几百路并发；老 Ethernet/单队列网卡多并发会在 NIC 处串行化。所以 MULTIPLE 的实际收益强烈依赖网络硬件。

Slide 28 — MPI Operations（MPI 操作的四阶段抽象）

这一页定义了一个核心概念：MPI operation（MPI 操作）。它是一个抽象，指"完成一次通信所需的所有步骤"。这个抽象让我们能统一描述 blocking / non-blocking / persistent 三种通信形式 —— 它们其实都在做这四个阶段，只是把阶段切分到不同的函数调用里。

定义

An MPI operation is a sequence of steps performed by the MPI library to establish and enable data transfer and/or synchronization —— MPI operation 是 MPI 库为了建立并完成一次数据传输或同步所走的整个流程。

四阶段

  • Initialization（初始化） —— 把参数列表交给 operation，但不把 buffer 内容交出去。相当于"我先告诉你我要做什么，但还没把货给你"。
  • Starting（启动） —— 把 buffer 的控制权交给 operation。从这一刻起 MPI 可能在读/写 buffer，你不能动。
  • Completion（完成） —— operation 把 buffer 控制权还给你，并表示输出已经更新好。slide 强调：operation 何时算"complete"，取决于实现 completion 的那个 MPI 函数何时返回。
  • Freeing（释放） —— 释放剩下的参数（如 buffer 地址、数组参数），收尾。

"initiation" 一词是 initialization + starting 两阶段的合称（注意和 initialization 单独那阶段区分）。

三种形式

slide 末尾点出：MPI operations are available in one or more of these forms: blocking, non-blocking, and persistent. 这三种形式的差别就在于：同一个 operation 的四个阶段，被拆到几个函数调用里去。下一页 slide 29 用图说明。

💡 抽象作用：你以后看到 MPI_Send（blocking）和 MPI_Isend（non-blocking）时，记得它们都在跑同样的四阶段，只是打包方式不同。这样就理解了"non-blocking 为什么需要再调一次 MPI_Wait" —— 因为那次调用是负责 completion + freeing 的。

Slide 29 — Forms of MPI Operations（三种形式：blocking / non-blocking / persistent）

这一页用图把 slide 28 的四阶段在三种形式里如何切分讲明白。

Blocking operation（阻塞）

四个阶段全部塞进一个函数调用。MPI_Send 一调，从 init 到 freeing 全干完才返回。

图示：Start → [Initialization | Starting | Completion | Freeing] → End。整个过程是一段连续的同步执行。

Non-blocking operation（非阻塞）

四个阶段被切成两半：

  • 第一个调用（如 MPI_Isend）—— 完成 Initialization + Starting，立刻返回。MPI 在后台启动通信子系统跑通信。
  • 第二个调用（如 MPI_Wait）—— 完成 Completion + Freeing。这个调用本身可以是 blocking 或 non-blocking。

图示：Start → [Init | Start] → End；中间通信子系统在跑；用户进程稍后再调一次 → [Completion | Freeing] → End。期间用户进程可以做别的工作 —— 这就是 slide 20 讲的 compute-transfer overlap 的实现机制。

Persistent operation（持久化）

四个阶段每一个都有独立的函数调用。可重复利用一次"建立好的通信通道"反复发同样配置的消息（比如循环里每步都和同一个邻居交换同样大小的数据）。每一阶段调用都可以是 blocking 或 non-blocking。

图示有 Inactive (Initialized) 和 Active (Started, 通信子系统在跑) 两个状态，最后到 Completed。

slide 明确说："Persistent operations will not be part of CS 2050." —— 这门课不考，了解概念即可。

底部紫色框的补充

"Additionally, an MPI operation can be collective or non-collective" —— 上面三种形式（blocking/non-blocking/persistent）是一个分类维度；collective vs non-collective 是另一个独立维度。两个维度正交：例如可以有"非阻塞集合通信"（MPI_Ibcast），也可以有"阻塞点对点"（MPI_Send）。

💡 核心区分：blocking = "一次调用全包"；non-blocking = "起一次 + 等一次，中间能干活"；persistent = "建一次通道反复用"。课程考前两种，第三种了解就行。

Slide 30 — Blocking Point-to-Point Communication（阻塞点对点：MPI_Send / MPI_Recv 详解）

这一页正式介绍 MPI 最基本的两个函数：MPI_Send 和 MPI_Recv。

函数签名（颜色对应 envelope/body）

int MPI_Send(
    void *buf, int count, MPI_Datatype datatype,   // body
    int dest, int tag, MPI_Comm comm               // envelope
);

int MPI_Recv(
    void *buf, int count, MPI_Datatype datatype,   // body
    int source, int tag, MPI_Comm comm,            // envelope
    MPI_Status *status                             // 元数据回填
);

参数顺序就是 slide 21 讲过的"body 三件套 + envelope 三件套"。MPI_Recv 末尾多一个 status。

非局部（non-local）的含义

slide 紫色框："They are both non-local procedures. An MPI_Send requires a matching MPI_Recv to complete and vice versa."

"non-local" 在 MPI 术语里意思是这个调用是否完成不只取决于本地状态，还取决于另一个进程。MPI_Send 要"完成"就必须有一个匹配的 MPI_Recv 在对方进程上 —— 否则它可能一直挂着。这是阻塞点对点通信的本质。

什么叫"匹配"？

An MPI_Send matches an MPI_Recv only if dest, source, tag and comm match.

四个 envelope 字段必须同时对得上：

  • 发送方写的 dest = 接收方进程的 rank。
  • 接收方写的 source = 发送方进程的 rank。
  • 双方 tag 相同。
  • 双方在同一个 communicator 里。

通配符：当 source 或 tag 未知时

  • MPI_ANY_TAG —— 接收方"我不关心 tag 是几，任意 tag 都收"。
  • MPI_ANY_SOURCE —— 接收方"我不关心是谁发的，任何进程发的都收"。

用了通配符后，status 就有用了 —— 可以查出实际收到的消息真正是从哪个 source、哪个 tag 来的。如果你不需要这些信息（多数情况），传 MPI_STATUS_IGNORE 让 MPI 跳过填充。

错误码

返回值是错误码，成功时是 MPI_SUCCESS。完整列表可以 man MPI 查。

💡 四个关键点：(1) 参数顺序 = body + envelope；(2) Send 一定要有匹配的 Recv，否则挂死；(3) 匹配条件 = dest/source/tag/comm 全对得上；(4) 通配符 + status 用于"我不知道谁会发来"的场景，否则传 MPI_STATUS_IGNORE 即可。
用 MPI_ANY_SOURCE 还算 point-to-point 吗？是不是变成 broadcast / 集体通信了？

仍然是 point-to-point。MPI_ANY_SOURCE 只是接收方的通配符，放宽了"我要收谁的"这一条匹配规则。它没改变通信的根本机制 —— 一次 MPI_Recv 仍然恰好接收一条消息，发送方依然必须明确写 dest。

关键事实：

  • 哪条消息被匹配，由库的匹配引擎决定（通常按到达顺序）。status.MPI_SOURCE 告诉你这次到底收的是谁的。
  • 不参与的进程没事 —— point-to-point 不要求 group 全员参与，只有调 Send / Recv 的进程才参与。

和 broadcast/collective 的本质区别：

P2P + ANY_SOURCEBroadcast (collective)
谁参与只调 Send/Recv 的进程全员必须参与
API 形态Send / Recv 是两个不同函数所有进程调同一个 MPI_Bcast
一次调用收几条1 条一次发给所有人
不参与的进程会怎样没事整个程序死锁（collective 必须到齐）

典型用途：master-worker 模式。master 不知道哪个 worker 先算完，用 ANY_SOURCE 收第一个上报的结果：

// rank 1, 2, 3 各自完成后：
MPI_Send(&my_result, 1, MPI_INT, 0, TAG_RESULT, MPI_COMM_WORLD);

// rank 0 循环收 3 次，谁先到收谁
for (int i = 0; i < 3; i++) {
    MPI_Status status;
    MPI_Recv(&result, 1, MPI_INT, MPI_ANY_SOURCE, TAG_RESULT,
             MPI_COMM_WORLD, &status);
    printf("Got from rank %d\n", status.MPI_SOURCE);
}

这里发生了 3 次独立的 point-to-point 通信，互相不"广播"给别人，每条消息只到 rank 0。要广播必须显式调 MPI_Bcast / MPI_Reduce / MPI_Gather 等 collective API。

Slide 32 — Blocking Point-to-Point Example（example-4：能跑通的"危险"代码）

这一页给出 example-4 的代码，让你预测它会怎么样、有没有 bug。下一页给答案。

代码：两个进程交换 rank ID

MPI_Init(&argc, &argv);
MPI_Comm_rank(MPI_COMM_WORLD, &rank);

if (0 == rank) {
    MPI_Send(&rank, 1, MPI_INT, 1, 98, MPI_COMM_WORLD);
    MPI_Recv(&recv, 1, MPI_INT, 1, 99, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
} else {
    MPI_Send(&rank, 1, MPI_INT, 0, 99, MPI_COMM_WORLD);
    MPI_Recv(&recv, 1, MPI_INT, 0, 98, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
}
std::cout << "Rank " << rank << " got ID " << recv << " from other rank\n";
MPI_Finalize();

逻辑：rank 0 和 rank 1 互相发自己的 rank 给对方。注意两边都是先 MPI_Send 后 MPI_Recv。

实际输出

$ mpirun -n 2 ./mpi_p2p
Rank 0 got ID 1 from other rank
Rank 1 got ID 0 from other rank

看起来一切正常 —— 程序成功结束、两边都收到对方 ID。slide 紫色框抛出问题："Is this code bug free?""输出符合预期吗？"答案在 slide 33。

💡 悬念：这段代码两边都是"先 Send 后 Recv"，如果 Send 是真正的阻塞调用，应该会双方都卡在 Send 等对方 Recv，形成死锁。但实测能跑通 —— 为什么？slide 33 揭晓。
这里为什么用 MPI_Init 而不是 MPI_Init_thread？

因为这段代码没有任何多线程 —— 没 OpenMP、没 pthread、没 std::thread。每个 MPI process 从头到尾只有一个 main 线程在跑，所以 MPI_Init（等价于 MPI_THREAD_SINGLE 契约："我承诺只有一个线程"）自动满足。

只要代码里出现 #pragma omp parallel / pthread_create / std::thread 等任何线程构造，就必须切到 MPI_Init_thread 显式声明级别 —— 哪怕只让 master 调 MPI（FUNNELED）。否则违反 SINGLE 契约，行为 undefined。

代码里没有任何 "blocking" flag，blocking 是怎么决定的？

MPI 把 form（blocking/non-blocking/persistent）编码在函数名里，不是参数：

FormSend 名Recv 名助记
BlockingMPI_SendMPI_Recv裸名 = 一次性完成四阶段
Non-blockingMPI_IsendMPI_IrecvI=Immediate，立即返回
PersistentMPI_Send_initMPI_Recv_init_init=建模板，靠 MPI_Start 启动

这正是 slide 28 四阶段抽象的体现：blocking 把 init/start/complete/free 四阶段打包到 1 个调用，non-blocking 拆成 2 个（Isend + Wait），persistent 拆成 3+ 个。换 form 是改函数名，不是改 flag。slide 32 选了 MPI_Send/MPI_Recv，所以这是 blocking 形式。

Slide 33 — Same Example, with Answer（这段代码其实有 bug）

承接上一页：这段代码 bug-free 吗？答案：No!

理论分析（紫色框）

"The (blocking) routines we use are non-local. The blocking MPI_Send will never be matched with a MPI_Recv. The execution will not make progress → deadlock. Yet, our program did not deadlock. Why?"

按 MPI 的规范，这段代码应该死锁：

  • rank 0 卡在 MPI_Send，等 rank 1 来收。
  • rank 1 也卡在 MPI_Send，等 rank 0 来收。
  • 双方都没机会执行 MPI_Recv —— 经典死锁。

但实际跑起来没死锁。这意味着"实际行为"和"规范要求"出现了偏差。下一页解释为什么：MPI 的实现允许做一种"buffering"小动作，在小消息时偷偷绕过这种死锁，但这是不可移植的。

💡 关键认知：能跑通≠没 bug。MPI 程序在小消息上"碰巧能跑"非常常见，但只要消息变大或进程数变多就会暴雷。下一页揭示原因。

Slide 34 — MPI Communication Modes（标准模式与 buffering 的真相）

这一页解释为什么 example-4 能"碰巧跑通"，并引出 communication modes（通信模式）这个新概念。

真相：我们只是运气好

"We were just lucky. Sending a larger message would not have worked (or if many more processes were involved than just two)." —— 消息大一点或进程多一点就死锁。

原因：standard mode + 内部 buffering

MPI_Send 用的是 standard mode（标准模式）。在这个模式下：

  • MPI 自己决定要不要 buffer 消息。如果 MPI 觉得消息够小，它会先把消息拷到一个内部缓冲区，MPI_Send 立刻返回 —— 即使对方还没调 Recv。
  • 这就是 example-4 没死锁的原因：消息只有一个 int（4 字节），MPI 内部 buffer 装得下，两边的 Send 都立刻返回，然后都跑到 Recv，正常完成。
  • 但是默认 buffer 很小 —— slide 紫色框："the default buffer size in any MPI implementation is very small!" 一旦消息超过这个尺寸，MPI 就不再 buffer，Send 必须等到对方 Recv 配对，example-4 就会真的死锁。

standard mode 的精确语义

slide 紫色框：MPI_Send = standard mode，它的行为：

  • How standard mode behaves is not defined in the standard, therefore implementation dependent —— 究竟 buffer 不 buffer，由 MPI 实现自己决定，标准不规定。
  • 唯一保证：当 MPI_Send 返回时，发送 buffer 可以安全重用了。不保证消息已经发到对方。
  • MPI_Send 是 non-local 过程，"成功完成"可能依赖于对方是否调用了 Recv。

为什么叫"communication modes"

除了 standard，MPI 还有别的发送模式（buffered/synchronous/ready），每种对"何时返回"和"是否要等 Recv"有不同的保证。这些是选择 communication protocol（通信协议）的开关。这门课主要讲 standard mode，知道还有别的就行。

💡 实战教训：(1) 永远不要依赖 standard mode 会 buffer 来"绕过"死锁 —— 不可移植，换个 MPI 实现就崩；(2) 写两端都收发的逻辑时，要么严格 send-recv 错开（rank 0 send 时 rank 1 recv），要么用一次性安全的 MPI_Sendrecv。
Blocking Send 的"完成"判定标准是什么？eager 和 rendezvous 怎么回事？

判定标准只有一个：当 MPI_Send 返回，意味着 send buffer 可以安全复用。但 MPI 库实现这个标准的路径有两套，按消息大小自动选择：

路径触发机制Send 返回时对方是否已拿到
Eager消息小（~< 64 KB，实现相关）Copy 到 MPI 内部 buffer，原 buffer 立即可复用不一定（数据可能还在内部 buffer 漂着）
Rendezvous消息大和接收方 handshake，零拷贝直传到对方 user buffer已拿到（协议要求对方 Recv 启动后才传）

Rendezvous handshake 协议：

Sender                          Receiver
──────                          ────────
"我要发 N 字节" ─── RTS ────────→
                                等自己的 MPI_Recv 启动
              ←── CTS ─────  "buffer 准备好了，发吧"
"传 N 字节" ────────────────→  数据直接落到对方 user buffer
Send 返回

注意：rendezvous 里 Send 等的是对方"准备好接收"的信号 (CTS)，不是"确认收到"的回复。Eager 完全没这个 handshake，copy 完就走人。

串回 example-4 的 deadlock 根源：双方都是"先 Send 后 Recv"模式。

  • 小消息走 eager → 双方 Send 都直接 copy 后返回 → 各自走到 Recv → 跑通。
  • 大消息走 rendezvous → 双方 Send 都要对方先 Recv 给 CTS → 双方都没机会到 Recv → deadlock。

这就是 slide 上说的 "we were just lucky"：标准没保证小消息一定 eager，"能跑"完全靠实现细节碰巧成立。

三种修法：

// 方法 1：调换顺序，让一方先 Recv
if (rank == 0) { MPI_Send(...); MPI_Recv(...); }
else           { MPI_Recv(...); MPI_Send(...); }   // 先 Recv

// 方法 2：用 MPI_Sendrecv（推荐，对称写法）
MPI_Sendrecv(&rank, 1, MPI_INT, partner, 98,
             &recv, 1, MPI_INT, partner, 99,
             MPI_COMM_WORLD, MPI_STATUS_IGNORE);

// 方法 3：用 non-blocking，立即返回
MPI_Request reqs[2];
MPI_Isend(&rank, 1, MPI_INT, partner, 98, MPI_COMM_WORLD, &reqs[0]);
MPI_Irecv(&recv, 1, MPI_INT, partner, 99, MPI_COMM_WORLD, &reqs[1]);
MPI_Waitall(2, reqs, MPI_STATUSES_IGNORE);

Slide 35 — Blocking Point-to-Point Example Revisited（修正后的代码：顺序很重要）

这一页给出 example-4 的修正版，演示如何写出真正 deadlock-free 的代码。

修正：交错 send/recv 顺序

if (0 == rank) {
    MPI_Send(&rank, 1, MPI_INT, 1, 98, MPI_COMM_WORLD);
    MPI_Recv(&recv, 1, MPI_INT, 1, 99, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
} else {
    MPI_Recv(&recv, 1, MPI_INT, 0, 98, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
    MPI_Send(&rank, 1, MPI_INT, 0, 99, MPI_COMM_WORLD);
}

关键：rank 1 先 Recv 再 Send。这样 rank 0 的 MPI_Send(...,dest=1,tag=98) 立刻能匹配上 rank 1 的 MPI_Recv(...,source=0,tag=98)，不再依赖运气好的 buffering。

规则（slide 紫色框）

Rule: when you write MPI code, try to post the matching MPI_Recv of an MPI operation as early as possible.

"尽早 post Recv" —— 因为 Recv 不是 non-local 的瓶颈源（Recv 本身只是声明"我准备好接收"），尽早调它有助于通信尽早匹配，避免 Send 端等待。

关键认知（橙色提示）

"The order of (blocking) MPI procedures matters!" —— blocking 调用的顺序是程序行为的一部分。同样几行代码换个顺序就从死锁变成正确，这是 MPI 编程和单线程编程一个重要区别。

💡 设计准则：(1) 双向交换数据时让一方先 recv，另一方先 send；(2) 更省事的做法是用 MPI_Sendrecv，它把 send + recv 打包在一次调用里，MPI 实现保证不死锁；(3) 阻塞 MPI 调用的相对顺序就是它的语义，不能任意调换。

Slide 36 — Computing π with Blocking Point-to-Point（example-5：手写 reduction 算 π）

这一页用 MPI 做和上一讲 OpenMP 一样的事 —— 用 Leibniz 级数算 π：

π = 4 · Σk=0∞ (−1)k / (2k+1)

但这次不再是线程间分工，而是进程间分工 + 显式通信合并结果。

三步骤算法

  1. 分块 —— 总共算 n=10⁸ 项。每个 rank 算其中一段：chunk_size = (n + size - 1) / size，my_start = rank * chunk_size，my_end = min(n, my_start + chunk_size)。
  2. 本地求部分和 —— 每个 rank 在自己那段循环里累加 (-1)^k / (2k+1) 到本地 sum。没有 race condition —— 各进程的内存独立。
  3. 归约 —— 把 size-1 个非 root rank 的部分和都收到 rank 0。

归约部分的代码（重点）

if (0 != rank) {
    MPI_Send(&sum, 1, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD);
} else {
    for (int s = 1; s < size; ++s) {
        MPI_Recv(&recv, 1, MPI_DOUBLE, s, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);
        sum += recv;
    }
    std::cout << 4 * sum;
}

非 root rank 各自把自己的 partial sum 发给 rank 0；rank 0 在循环里依次收，累加进自己的 sum。

slide 强调的几点

  • "There are no race conditions here!" —— 这是 MPI 相对 OpenMP 的优势。OpenMP 里多个线程同时累加同一个 sum 必须用 reduction 或 atomic；MPI 里每个进程有自己的 sum，根本没竞争。
  • "It is a collective operation" —— 把所有进程的部分结果合并到一个进程，是逻辑上的集合操作。但这里我们用纯 point-to-point 实现 —— 即下一页要批评的"naive 实现"。
  • "This will scale badly" —— 这种实现下 rank 0 要顺序收 size-1 次，串行化了。1000 个进程时 rank 0 要做 999 次 Recv，性能崩。MPI 提供的 MPI_Reduce 用树形算法，只要 log₂(1000) ≈ 10 步，下一页讲。
💡 承上启下：这个例子是故意写得 naive 的，目的是让你看到"为什么需要 collective primitive"。下一页 slide 37 开始正式讲集合通信，slide 40 给出真正该用的 MPI_Reduce。

Slide 37 — Blocking Collective Communication（集合通信的总览与分类）

这一页正式进入 collective（集合通信）。集合通信涉及一个 communicator 里的所有 rank，是最常用的 MPI 操作类型。

四条核心规则

  • Commonly used operations that involve all ranks in a communicator —— 集合通信涉及 communicator 里的每一个 rank。
  • When a blocking collective procedure returns, it is safe to use the communication buffers again（completion） —— 阻塞集合返回时，buffer 安全。这就是 slide 28 讲的 completion 阶段。
  • 不要假设"集合返回 = 所有 rank 都到了同一点"（紫色框）—— 一个 rank 调用集合返回，不保证其他 rank 也已经到这一步。MPI 实现可能让先到的 rank 先返回继续走。唯一保证同步的集合是 MPI_Barrier。
  • 有些集合操作有"特殊角色" rank，叫 root —— 例如 MPI_Bcast（root 是源头）、MPI_Reduce（root 是结果接收方）。其他 rank 在调用时也要传同样的 root 参数。
  • 所有 rank 必须调用相同的集合原语，否则死锁 —— 集合通信没"对方在不在"的概念，全员到位才能完成。一个 rank 漏调或调错就全卡死。

集合操作分类（四个色框）

  • All to One（多→一）：MPI_Reduce（reduce 到 root）、MPI_Gather（收集到 root）。
  • One to All（一→多）：MPI_Bcast（root 广播）、MPI_Scatter（root 分发不同片段给各 rank）。
  • All to All（多→多）：MPI_Allgather（所有 rank 都收齐所有人的数据）、MPI_Alltoall（每对 rank 互换不同片段）、MPI_Allreduce（reduce 后结果发给所有人）、MPI_Barrier（同步点）。
  • Other（前缀类）：MPI_Scan（前缀和）、MPI_Exscan（不含自己的前缀和）。
💡 记忆策略：把分类按"参与方向"记 —— "聚集"（All to One）、"分发"（One to All）、"全员混合"（All to All）、"前缀"（Other）。每个名字里的 All... 前缀表示"结果让所有 rank 都看到一份"。MPI_Barrier 是唯一保证全员同步的。
"Blocking collective returns 时 buffer 安全" 具体什么意思？

这和 slide 32-34 讲过的 "blocking MPI_Send 返回 = buffer 可安全复用" 是完全同一套语义，只是搬到 collective 上：当 MPI_Bcast/MPI_Reduce/MPI_Allreduce/... 在本进程返回时，传给它的 sendbuf/recvbuf 解禁 —— MPI 库不会再读 sendbuf 也不会再写 recvbuf，你可以放心改/复用。

不同 collective 在返回时的 buffer 状态：

Collective本进程 sendbuf本进程 recvbuf
MPI_Bcast（root）数据已交给 MPI，可改—
MPI_Bcast（非 root）—已收到数据
MPI_Reduce（非 root）已交出，可改—
MPI_Reduce（root）已交出，可改已含归约结果
MPI_Allreduce已交出，可改已含归约结果

关键：这是关于"本进程 buffer 所有权"的局部声明，不是关于 collective 全局完成的声明。不同进程的返回时机可能差很多（tree 算法下 root 和叶子节点返回时间不同），每个进程只为自己的 buffer 负责。这正是上面紫色框那条 "不要假设集合返回 = 所有 rank 都到同一点" 的具体体现。

Non-blocking 版本（MPI_Ibcast/MPI_Ireduce/...）把 buffer 解禁推后到 MPI_Wait：

MPI_Request req;
MPI_Ibcast(&data, 1, MPI_INT, 0, MPI_COMM_WORLD, &req);
// 立即返回，但 data buffer 还不安全 —— MPI 后台可能在用
// data = 99;   ❌ UB

MPI_Wait(&req, MPI_STATUS_IGNORE);
data = 99;     // ✓ 现在才解禁

对应 slide 28 四阶段：blocking collective 一次调用打包 init/start/complete/free 四阶段；non-blocking 拆成 Ibcast（init+start）+ Wait（complete+free）。"Buffer 解禁"对应 complete 阶段。

Slide 38–39 — Why We Have Collective Procedures（为什么需要 collective：以 Bcast 为例）

这一页（与 slide 39 同主题，39 多了一个数字对比的 note）讲"既然 collective 都能用 send/recv 拼出来，为什么还要专门的 collective API"。答案：实现得好太难，让 MPI 替你做。

核心论点（紫色框）

"Collectives exist because we might implement them poorly ourselves." —— collective 存在的理由就是"自己写很容易写得很烂"。

更具体地："MPI does not want you to invent your own. The MPI implementation will pick the best automatically depending on the hardware, the size of the communicator, or due to algorithmic preference." —— MPI 实现会根据网络拓扑、节点数、消息大小等自动选最优算法。你手写很难考虑到这些维度。

例子：MPI_Bcast 的两种实现

Naive 实现（红色图） —— root rank 把数据顺序发给每个其他 rank：

  • P0 → P1, P0 → P2, ..., P0 → P7（共 7 次 send）。
  • 对 8 个 rank 要做 7 次 Send，对 n 个 rank 要做 n-1 次。
  • 问题：root 完全串行化，时间 = O(n)。

Log-step 实现（绿色图，树形） —— root 先发给一个 rank，然后两人各发给一个新人，四人各发给一个新人...指数扩散：

  • 第 1 步：P0 → P4。
  • 第 2 步：P0 → P2, P4 → P6。
  • 第 3 步：P0 → P1, P2 → P3, P4 → P5, P6 → P7。
  • 关键：已经收到数据的 rank 帮忙转发，每一步参与发送的 rank 数翻倍。
  • 对 n 个 rank 只要 ⌈log₂(n)⌉ 步，时间 = O(log n)。

规模差异（slide 39 紫色框）

  • 8 ranks：3 步 vs 7 步 —— 提升一般，可能感觉不出来。
  • 1024 ranks：10 步 vs 1023 步 —— 100× 提升。

规模越大差距越夸张，这就是 collective 在 HPC 里不可替代的根本原因。

💡 实战准则：能用 collective 就别手写循环。MPI 实现做了大量算法选择（树形、流水线、硬件多播）让你白拿性能。slide 36 那种 for s=1..size: MPI_Recv 在 1000 进程时是灾难，正确做法是 MPI_Reduce（slide 40）。
感觉 collective 都很垂直，send/recv 才是万能的？

这个直觉部分对、部分反了。实战里的频率排序大致是：

Allreduce ≫ Reduce ≈ Bcast ≫ Send/Recv ≫ Gather/Scatter ≫ Alltoall ≫ Scan/Exscan

意外的是几个 collective 比 send/recv 更常用：

  • Allreduce —— 分布式 ML 训练的核心。每个 batch 都要把所有 GPU 的梯度求平均，就是一次 Allreduce。当今 HPC 里被调用次数最多的 MPI 函数。
  • Reduce / Bcast —— 算全局 max/min/sum、分发初始数据，几乎所有并行程序都会用。
  • Send/Recv —— 主战场实际上是邻居模式，例如 stencil/CFD 的 halo exchange，每个 rank 只跟空间上相邻的 rank 换边界。这种不规则、非全员通信才是它的天下。
  • Scan / Exscan / MAXLOC —— 你的直觉对了，这几个应用确实窄。

修正后的心智模型

  • Collective = 高层 API：覆盖 80% 的常见模式（全员合并、广播、全员交换）。能用就用，代码短、性能好。
  • Send/Recv = 底层 API：剩下 20% 不规则的场景。灵活但代码长、易写错（slide 32–35 的死锁就是典型坑）。

类比：collective 像 NumPy 的 sum() / cumsum()；send/recv 像手写 for 循环。前者看起来"专门"，但实际覆盖了大部分日常需求。

那 P0 直接"同时"发给所有 rank 不行吗？为什么必须 tree？

"同时"在 logical 层写得出，但 physical 层不可能真同时 —— P0 是单点资源，发送能力固定。

尝试 1：用 MPI_Isend 让 N-1 条 send "同时"发出

// P0 看似同时发给所有人
MPI_Request reqs[size-1];
for (int i = 1; i < size; i++) {
    MPI_Isend(&data, 1, MPI_INT, i, 0, MPI_COMM_WORLD, &reqs[i-1]);
}
MPI_Waitall(size-1, reqs, MPI_STATUSES_IGNORE);

Logical 上 N-1 个 request 同时在飞，但物理传输还是受 P0 自己硬件约束：

  • P0 只有一张网卡：所有出站数据走这一张 NIC，带宽固定。N 条 Isend 在网卡处仍要排队，多队列网卡也不会给你 N 倍带宽。
  • P0 只有一份内存带宽：同一份 data 被 copy/DMA 出 N 次。
  • P0 只有一个 CPU：构造 N 份消息头、维护 request 状态都要 CPU。

结论：P0 一个进程发 N-1 份数据的总耗时仍是 O(N)，Isend 只是把"等待"从用户线程挪到了后台。

Tree 算法的本质：让接收方变成发送方，分摊带宽

Step 1: P0 → P1                                      (1 个发送方)
Step 2: P0 → P2,  P1 → P3                            (2 个发送方)
Step 3: P0 → P4,  P1 → P5,  P2 → P6,  P3 → P7        (4 个发送方)

每一步发送方数量翻倍，每个发送方只发一份数据。Step 3 那一刻有 4 张网卡同时工作，是 P0 单点广播永远做不到的。Tree 算法没让任何单条链路变快，它做的是让多条链路同时被使用，把固定的"总传输工作量"分布到多个 sender 上并行完成。

那能不能真"P0 一次广播"？

  • 网络层 multicast：以太网/IP 支持，但不是所有 HPC 网络（InfiniBand/Cray）都有 portable multicast，可靠性/流控也要重新设计。MPI 标准要在所有网络上跑，默认实现不能依赖。
  • 同节点共享内存广播：同节点多 rank 共享 RAM，P0 写一次大家读一次。MPI 实现内部确实在同节点会用 shm 通道（slide 23 Q&A 提过），但跨节点不适用。
  • 硬件 collective offload：Mellanox SHARP / Cray Aries 等高端互连有专门硬件引擎能在交换机上做广播，但属于实现优化，不是标准要求。

所以默认实现选 tree —— 只依赖最基本的 point-to-point 能力，在任何 MPI 实现 + 任何网络上都能跑，且能拿到 O(log N) 扩展性。

Slide 40 — Reduction Operation（MPI_Reduce 的完整接口与运算符）

这一页给出 MPI_Reduce 的完整签名 —— 上一讲（slide 36）我们手写的"所有 rank 把 partial sum 发给 root"操作，正确的做法 就是这一个函数。

函数签名

int MPI_Reduce(
    const void *sendbuf,    // 输入：自己要参与归约的数据
    void       *recvbuf,    // 输出：归约结果（仅 root 上有效）
    int         count,      // 元素个数
    MPI_Datatype datatype,  // 元素类型
    MPI_Op      op,         // 归约运算符（如 MPI_SUM）
    int         root,       // 收结果的 rank
    MPI_Comm    comm        // 通信器
);

所有 rank 都调这个函数（collective），传一样的 op、root、comm，每个 rank 把自己的 sendbuf 传进去。MPI 内部把所有 rank 的 sendbuf 按 op 合并，结果写到 root 的 recvbuf。非 root rank 的 recvbuf 不被使用，可传 nullptr（具体看实现，但语义上你不能依赖它）。

内置归约运算符

MPI_Op语义
MPI_MAX / MPI_MIN最大值 / 最小值
MPI_SUM / MPI_PROD求和 / 求积
MPI_LAND / MPI_LOR / MPI_LXOR逻辑 and / or / xor
MPI_BAND / MPI_BOR / MPI_BXOR位运算 and / or / xor
MPI_MAXLOC / MPI_MINLOC最值及其位置（同时返回 value 和 rank）

三条要注意的规则

  • Reduction 是 collective —— 所有 rank 都必须参与，少一个就死锁。
  • 运算必须 associative（结合律） —— 因为 MPI 实现会用树形顺序合并，结合律保证结果与顺序无关。
  • commutative（交换律）不是必需 —— 标准不要求；但如果你的 op 不可交换，MPI 会强制按 rank 顺序合并（性能略差）。

原地归约（in-place）

如果你不想多分配 sendbuf，可以让 recvbuf 同时充当输入：把 sendbuf 设为 MPI_IN_PLACE，MPI 会从 recvbuf 读输入数据再写回结果。常见于"我已经把数据放好了，就在这里 reduce 然后覆盖结果"的场景。

自定义运算符

用 MPI_Op_create 可以注册自己的归约函数（比如把"复数乘法"做成 op）。本课程不涉及。

💡 用 MPI_Reduce 重写 slide 36 的 π 算法：把那段 if(rank!=0) Send; else for: Recv 整个换成一行 MPI_Reduce(&sum, &total, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);。少十几行代码、自动 O(log n) 树形合并、跨硬件最优。这就是为什么"看到 reduce 模式就用 MPI_Reduce"。

Slide 41 — Computing π with Blocking Reduction（用 MPI_Reduce 重写 π 算法）

这一页就是把 slide 36 那个手写归约的 π 程序，用 MPI_Reduce 替换掉，演示集合通信带来的代码与性能双赢。

关键改动

double pi = 0.0;
MPI_Reduce(&sum, &pi, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
if (0 == rank) {
    std::cout << "pi = " << 4 * pi << "\n";
}

之前 slide 36 那一整段 if(rank!=0) Send; else for: Recv 共 6–7 行，压缩成一行 MPI_Reduce。所有 rank 的 partial sum 都按 MPI_SUM 合并到 rank 0 的 pi 变量。

slide 强调的三点

  • Less code and more clear —— 代码短、意图直白。"我要把 sum 求和到 rank 0" 一目了然。
  • MPI takes care of the reduction for us —— 树形归约由 MPI 实现负责，自动 O(log n)。手写循环的 O(n) 串行瓶颈消失。
  • Result is reduced to rank 0 in this example —— root 写成 0 就让结果回到 rank 0。换成别的 rank 也行。

紫色框的红线（重要）

"All ranks must call MPI_Reduce otherwise the code will deadlock."

这是 collective 的铁律。slide 36 里非 root rank 调 Send、root 调 Recv，语义上不对称；换成 MPI_Reduce 后所有 rank 都调同一个函数，少一个就死锁。常见 bug：在某个 if 分支里漏调了集合操作。

💡 归纳：slide 36 是"反例"，slide 41 是"正例"。同样的逻辑，前者代码长 + O(n) 串行 + 易出 bug；后者一行 + O(log n) 树形 + MPI 自动选最优。每次写并行归约时优先想"有没有现成的 collective"。
把这行 MPI_Reduce 调用展开讲一下，root 体现在哪里？

MPI_Reduce 完整签名是 7 个参数，按位置一一对应：

MPI_Reduce(&sum, &pi, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
//          ①    ②   ③    ④          ⑤      ⑥        ⑦
#形参实参含义
①sendbuf&sum每个 rank 自己已经算好的本地分量地址
②recvbuf&pi结果写到哪里。仅 root 这个变量真的会被赋值，非 root 的 pi 不变
③count1元素个数（这里只 1 个）
④datatypeMPI_DOUBLE每个元素的类型
⑤opMPI_SUM归约运算符（加法）
⑥root0结果归集到 rank 0
⑦commMPI_COMM_WORLD在哪个 communicator 里做

Root 体现在两层：

  1. 参数层：第 6 个参数 0 字面上指定 root 是 rank 0。改成 2 就是结果送 rank 2。
  2. 运行层：所有 rank 都执行同一行代码（collective 铁律），但行为不对称 —— 只有 root 的 recvbuf 真正被赋值。
调用 MPI_Reduce 后
Rank 0（root=0）贡献 sum + 接收最终结果到 pi
Rank 1, 2, ...（非 root）只贡献 sum，自己的 pi 不被赋值

Before / After 数据流（4 个 rank 为例）：

调用前：
  Rank 0:  sum = S₀,  pi = ?
  Rank 1:  sum = S₁,  pi = ?
  Rank 2:  sum = S₂,  pi = ?
  Rank 3:  sum = S₃,  pi = ?

调用后：
  Rank 0:  sum = S₀,  pi = S₀+S₁+S₂+S₃   ← 结果在这里
  Rank 1:  sum = S₁,  pi = ?  ← 不动
  Rank 2:  sum = S₂,  pi = ?  ← 不动
  Rank 3:  sum = S₃,  pi = ?  ← 不动

所以代码后面跟 if (rank == 0) printf(...) —— 只有 rank 0 的 pi 有效。

Root 参数的两条隐性规则：

  • 所有 rank 必须传同一个 root 值。某个 rank 传不同的 root 是 UB（通常死锁或结果错乱）。
  • 非 root 的 recvbuf 即使没用也要传合法指针 —— C 函数签名要求合法地址，习惯传同一个 &pi。MPI 标准上它的内容不会被读也不会被写。

对比 MPI_Allreduce：如果想让所有 rank 都拿到结果，换成 MPI_Allreduce(&sum, &pi, 1, MPI_DOUBLE, MPI_SUM, MPI_COMM_WORLD) —— 签名少了 root 参数，因为语义就是"结果发给所有人"，不需要指定接收方。这反过来印证了 root 的角色：它就是"结果归集到哪里"的开关。

Slide 42 — In-Place Reduction（原地归约：MPI_IN_PLACE）

这一页是 slide 41 的小变种 —— 用 MPI_IN_PLACE 让 root 节省一个 buffer。

原地版本的写法

if (0 == rank) {
    MPI_Reduce(MPI_IN_PLACE, &sum, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
} else {
    MPI_Reduce(&sum, nullptr, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
}
if (0 == rank) {
    std::cout << "pi = " << 4 * sum << "\n";
}
  • root 端：把 sendbuf 设为 MPI_IN_PLACE，recvbuf 写 &sum。意思是"输入也用 recvbuf，结果原地覆盖回去"。
  • 非 root 端：和普通版一样，传 &sum 作 sendbuf，recvbuf 反正不用，传 nullptr 也行。

slide 给的三条评论

  • You could save allocating another double by using MPI_IN_PLACE —— 主要好处是不用为 root 单独分配一个新变量。如果是大数组（不是单个 double），这种省略就有意义了。
  • This is not always clearer —— 但代码可读性反而下降：非 root 和 root 走不同分支，要分开写。slide 老实承认这点。
  • In this example, allocating one more double is not a big deal —— 对单个 double，这种优化不值得。MPI_IN_PLACE 真正的应用场景是大型数组，比如几百 MB 的矩阵。
💡 什么时候用 in-place：buffer 巨大、内存吃紧时。不要为了"少声明一个变量"就到处用 —— 写法分叉、可读性下降，一般情况下普通版本（slide 41）就好。
非 root 的 recvbuf 为啥可以"随便"传？nullptr 这种写法对吗？

非 root 在 reduce 里根本不写 recvbuf。直观上你可能以为"非 root 把数据送出去时也要先放进某个 recv-side buffer 再被收走"——其实不是。树形归约的中间收发都发生在 MPI 内部缓冲里：每个非 root 把 sendbuf 的数据递给上一层，最终汇到 root 才写进用户层的 recvbuf。所以非 root 那个 recvbuf 仅仅是 C 函数签名上的占位实参。

但 slide 那里写 nullptr 其实不严谨：MPI 标准没保证实现不会去检查/解引用这个指针。更稳妥的写法是复用同一个变量（如 &sum），既给了合法地址也不会被改：

MPI_Reduce(&sum, &sum, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);  // 非 root 也安全
MPI_IN_PLACE 到底省了什么？是省 MPI 内部那个 buffer 吗？

不是。要分清三层 buffer：

层谁拥有IN_PLACE 影响？
用户 sendbuf用户代码—
用户 recvbuf用户代码就是省这个
MPI 内部缓冲（eager copy / rendezvous）MPI 库无关

IN_PLACE 只是让 root 的 sendbuf 和 recvbuf 共用同一块用户内存，省掉一个用户层变量声明。和 eager / rendezvous 那套内部缓冲机制完全正交。

对单个 double 毫无意义。真正有用的场景是 1GB 的梯度数组这种——少分配 1GB 是实打实的。代价：root 的原始输入被结果覆盖。

MPI_Reduce 会自动识别"非 root 的结果该收到 root 的哪个变量"吗？

不会。结果落到哪里完全由 root 自己传的 recvbuf 决定，和非 root 传什么没关系。

底层原因：进程间指针不互通——每个进程的指针是本进程的虚拟地址，root 进程拿不到非 root 进程的 &result，反过来也一样。MPI 库的协调机制是基于 rank 角色（"谁是 root"由第 6 个参数指定），不是基于指针传递。

所以同样一行 MPI_Reduce(MPI_IN_PLACE, &gradient, ..., 0, ...)：rank 0 的 gradient 被覆盖成最终结果，rank 1/2/3 的 gradient 一动不动。这个规则推广到所有 collective（Bcast、Scatter、Gather…）。

Slide 43 — Find Max/Min Location with Reduction（example-6：MAXLOC / MINLOC 同时拿值与位置）

这一页讲两个特殊归约运算符：MPI_MAXLOC 和 MPI_MINLOC。它们的特点是同时返回"最值"和"最值在哪个 rank 上"。常用于"找最差/最好的进程"这类调试和负载均衡场景。

为什么需要特殊数据类型

普通 MPI_MAX 只返回最大值。MPI_MAXLOC 要同时返回值和它的索引（rank），所以输入必须是"value + 索引"成对的结构。MPI 为此预定义了一组特殊 datatype：

  • MPI_FLOAT_INT —— { float, int } 对
  • MPI_DOUBLE_INT —— { double, int } 对
  • MPI_LONG_INT —— { long, int } 对
  • MPI_2INT —— { int, int } 对
  • MPI_SHORT_INT —— { short, int } 对
  • MPI_LONG_DOUBLE_INT —— { long double, int } 对

"int" 那一项就是位置（rank）。详见 MPI 4.0 标准 6.9.3 节。

用法（example-6 关键代码）

struct DoubleInt {
    double val;
    int    rank;
} send_val, recv_val;

send_val.val  = drand48();
send_val.rank = rank;

MPI_Reduce(&send_val, &recv_val, 1, MPI_DOUBLE_INT,
           MPI_MINLOC, 0, MPI_COMM_WORLD);

if (0 == rank) {
    std::cout << "Minimum: value = " << recv_val.val
              << " on rank "         << recv_val.rank << "\n";
}

每个 rank 把 {val, rank} 配对作为一个元素发出。MPI_MINLOC 在所有 pair 里挑出 val 最小的那一对，连同它的 rank 一起送回 root。

输出示例

$ mpirun -n 4 ./mpi_minloc
Rank 1: value = 0.0416303
Rank 2: value = 0.812433
Rank 3: value = 0.783235
Rank 0: value = 0.708626
Minimum: value = 0.0416303 on rank 1

4 个 rank 各自生成一个随机数，MPI_MINLOC 找出最小的（rank 1 的 0.0416303）并返回。

对比 MPI_MIN

如果只用 MPI_MIN 和 MPI_DOUBLE，你只能得到 0.0416303，不知道它属于哪个 rank。要再写一轮通信才能问出来。MPI_MINLOC 一次搞定，是它存在的全部理由。

💡 使用场景：(1) HPC 调试 —— 哪个进程是慢的瓶颈？用 MPI_MAXLOC 找出最大执行时间和它的 rank；(2) 负载均衡 —— 哪个 rank 的工作量最重？用 MAXLOC 反查。比"先 MAX 再二轮 Send 问 rank"高效得多。
这个 MPI_Reduce 的参数顺序是固定的吗？MPI 各 API 是不是统一的一套顺序？

这一行 MPI_Reduce(&send_val, &recv_val, 1, MPI_DOUBLE_INT, MPI_MINLOC, 0, MPI_COMM_WORLD) 和 slide 41 那行完全是同一个签名，只是 datatype 换成 MPI_DOUBLE_INT、op 换成 MPI_MINLOC。但 MPI 整套 API 不是逐参数严格一致——只有"分组一致"。

函数签名
MPI_Send(buf, count, datatype, dest, tag, comm)
MPI_Recv(buf, count, datatype, source, tag, comm, status)
MPI_Bcast(buf, count, datatype, root, comm)
MPI_Reduce(sendbuf, recvbuf, count, datatype, op, root, comm)
MPI_Allreduce(sendbuf, recvbuf, count, datatype, op, comm)
MPI_Scatter(sendbuf, sendcount, sendtype, recvbuf, recvcount, recvtype, root, comm)

真正稳定的只有两条骨架：

  1. buffer 三件套永远绑定且顺序不变：描述一块内存就一定是 (buf, count, datatype) 紧挨着。Reduce 因为输入输出元素数和类型必须一致，可以共用一份 count/datatype；Scatter 输入输出类型可不同，所以两套三件套都完整列出。
  2. comm 永远最后（MPI_Recv 例外，因为有 status 输出参数兜底）。

中间那段"业务参数"完全看函数语义：点对点要 dest/source + tag；广播要 root；归约要 op + root；Allreduce 不要 root（人人都收）。不能死记一套通用顺序，只能记三件套绑定 + comm 收尾这两条骨架，剩下查 man MPI_Xxx。
