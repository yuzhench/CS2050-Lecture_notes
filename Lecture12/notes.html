Slide 6 — BITS AND BYTES 小测：单精度浮点几位？

这页讲什么

课堂小测，问单精度（single precision）浮点数占多少 bit / byte。正确答案：32 bits = 4 bytes。

为什么是 32 bit：IEEE 754 binary32 格式

"single precision" 指的是 IEEE 754 标准里的 binary32 格式，把 32 个 bit 切成三段：

段位数作用
sign（符号位）10 = 正，1 = 负
exponent（阶码）8decode 后 -126 ~ +127，用 bias 127
mantissa / fraction（尾数）23规约形式下隐含一个前导 1，等效 24 bit 精度
合计32= 4 bytes

对应 C/C++ 里就是 float（32 位），CUDA 里是 float 或 __half（half 是 16 位 binary16，不是单精度）。其它三个干扰项分别是：

  • 16 bits = half precision（FP16），现在 ML 训练里很流行，但不是 "single"。
  • 64 bits = double precision（FP64，C 里的 double）。
  • 128 bits = quad precision（FP128，__float128），HPC 里偶尔见，硬件直接支持的很少。

为什么这个问题对 HPC 很关键

带宽和缓存都是按 byte 算的，bit 宽度直接决定能不能装进 cache、能多快跑过 memory bus：

  • 同一个 vector，存成 float 比 double 少占一半内存 → 同一级 cache 能装更多元素 → cache miss 更少。
  • GPU 上 FP32 通常比 FP64 快 2× 甚至 16×（消费级卡 FP64 throughput 被故意阉割）。
  • 选择 precision 是 HPC 的常规权衡：能用 float 就别用 double，除非数值稳定性要求 double。
常见疑问 — 为什么不直接全用 FP64 永远不出错？
  • FP64 占 8 字节，是 FP32 的 2 倍 → 内存带宽减半、cache 命中率减半，对 memory-bound 算法直接慢一倍。
  • 消费级 GPU（如 RTX 系列）的 FP64 计算单元数量通常是 FP32 的 1/32 ~ 1/64，peak FLOPS 差距巨大。
  • 但你是做物理仿真、长时间数值积分、刚性 ODE → FP32 的 ~7 位有效数字会爆，必须 FP64。在精度够用的前提下追求最低位宽。
💡 single = 32 bit = 4 byte。记忆链：half / single / double / quad = 16 / 32 / 64 / 128 bit。HPC 的常识——位宽直接决定带宽和 cache 命中。

Slide 7 — STRONG SCALING（Amdahl's Law）

定义：什么是 strong scaling

Strong scaling = 用 Amdahl's Law 表达的一种 speedup 分析。它的核心假设有两条：

  1. 问题规模固定（problem size is fixed）——由 sequential 版本定义；
  2. 不断加更多处理器，希望"更快地到达解"（arrive at the solution faster）。

记 T_s = 串行运行时间，T_p = 用 p 个处理器并行运行时间，f = 程序中无论如何无法并行的串行部分占比（serial fraction，0 ≤ f ≤ 1）。Speedup 写作：

Sp = Ts / Tp = 1 / ( f + (1 − f) / p )

直觉解读：把 T_s 拆成 f·T_s（怎么都得串行做完）+ (1-f)·T_s（可被 p 个 worker 平分）。后者并行后变成 (1-f)·T_s / p，无论 p 多大，前者那块串行时间不会缩。

关键推论：上限就是 1/f

令 p → ∞，(1-f)/p → 0，得：

S∞ = 1 / f

Slide 右下角那张图就在画这件事——四条曲线对应不同 f：

  • f = 0（黑色虚线 ideal）：完全可并行，speedup = p，是 45° 直线。
  • f = 0.001（绿）：上限 1000×，但要拿到一半需要约 1000 核。
  • f = 0.01（橙）：上限 100×。
  • f = 0.10（红）：上限只有 10×，哪怕给你一万核，也飞不过 10×。

图上的注释 "50% serial fraction → no speedup with 24 threads, 2× speedup at infinite number of threads" 说明哪怕只有 50% 串行，再多核也只能 2×——惊人地悲观。

"serial fraction is hard to determine in general"

Slide 第三个 bullet 警告：serial fraction 是这模型的支配因子，但实际程序里它很难量出来。原因：

  • "串行"不只是字面上的单线程代码，还包括同步原语（barriers, locks, reductions）、I/O、显存拷贝、串行分配器、关键路径上无法重叠的步骤。
  • f 通常依赖问题规模、输入分布、硬件——没有静态的常数。
  • Profiling 工具（VTune / Nsight Systems）的价值正是反推实际的 f——这就是后两页 Example 的动机。

什么时候用 strong scaling

Slide 最后一个 bullet："Strong scaling analysis makes sense for systems with few processors and negligible communication overhead → shared memory"。

  • "few processors" + "negligible communication overhead" 描述的就是 共享内存（shared-memory）多线程，比如 OpenMP 在单机几十核上跑。
  • 核数一上千、跨机通信开销不可忽略时（典型 MPI 场景），strong scaling 的曲线会更早撞墙；这时换 weak scaling 视角更公平（下页）。
常见疑问 — 例题：f = 0.05，给我 100 核，speedup 多少？

代入公式：

S100 = 1 / ( 0.05 + 0.95/100 ) = 1 / ( 0.05 + 0.0095 ) = 1 / 0.0595 ≈ 16.8×

而上限 1/f = 1/0.05 = 20×。100 核已经把可并行那 95% 压得很扁，剩下的 5% 串行就是天花板。

常见疑问 — 现实里我观察到的 speedup 总比 Amdahl 预测低，多了什么？
  • 通信/同步开销：barrier、reduce、all-to-all 在核多时 superlinear 增长。
  • 负载不均：partition 不平均，最慢线程拖整体。
  • 缓存竞争 / false sharing：多核访问同 cacheline。
  • 内存带宽饱和：核数虽多但共享一个 memory controller。
  • Amdahl 是理想下界——它假设并行那部分完美 1/p，没算 overhead。所以现实 ≤ Amdahl 预测。
💡 Strong scaling = 问题规模固定、加核求加速。Amdahl 公式 S_p = 1/(f + (1-f)/p)，上限 1/f。串行部分是天花板；适用场景：共享内存、核数不太大、通信开销可忽略。

Slide 8 — WEAK SCALING（Gustafson's Law）

定义：什么是 weak scaling

Weak scaling 换了一个根本不同的问题：

  1. 每核的 work 固定（execution time per processor is fixed）——加更多处理器就同时把问题规模放大；
  2. 目标不是"更快解一个固定问题"，而是"在同一时间里解一个更大的问题"（arrive at a larger solution in the same time）。

这正好是 HPC 用户实际的工作方式：拿到 1024 核不是为了把昨天的问题缩短到 1/1024，而是把昨天 1024 个 cell 的网格扩成 100 万个 cell。

Gustafson 的推导

设原本 1 核处理 work W_s 用时 T_s。weak scaling 下，p 核处理的总 work 是 W_p = p · W_s（每核仍然分到 W_s 那么多）。把可并行那部分写成 (1-f)，串行部分 f 不随 p 变。Speedup 定义：

Sp = (Wp/Tp) / (Ws/Ts) = p · Ts / Tp = p · Ts / ( Ts + To )

其中 T_o = T_o(n; p) 是非零的串行/通信 overhead，依赖问题规模 n 和处理器数 p。当 n → ∞、T_o 增长慢于 p · T_s 时，S_p → p——也就是线性加速。

右图：Amdahl vs Gustafson 同图对比

Slide 右边那张图同时画了两条 speedup 曲线，横轴是 serial fraction 1-f（注意是 1-f，不是 p）：

  • Amdahl（红）：strong scaling，串行越多 speedup 掉得越狠，靠近 1。
  • Gustafson（蓝）：weak scaling，speedup 几乎线性下降，斜率温和——同样的串行比例下 weak scaling 给的数字总是更乐观。

结论："observable speedup for 32 processors as a function of the parallel fraction in a code, expressed in term of Amdahl's Law and Gustafson's Law." ——同一份代码，用哪种 scaling 模型衡量，结果可能差一个数量级。这就是为什么 paper 报告 speedup 时必须说清是 strong 还是 weak。

什么时候用 weak scaling

  • 大型 cluster / 跨机 MPI：strong scaling 早就撞墙了，Amdahl 数字难看。
  • 问题本身可以"放大"——网格更细、粒子更多、时间步更长。
  • "这台超算能让我做以前做不了的更大问题吗？" → weak scaling。
  • "我能不能让今天的问题更快出结果？" → strong scaling。
常见疑问 — Strong 和 Weak 到底谁更"诚实"？
  • 都不"假"，但回答的是不同问题。混淆它们最容易被骗——"我们获得了 800× speedup！"如果是 weak scaling 在 1024 核上得到 800，那只是说 overhead 还能接受；如果是 strong scaling 拿到 800，则非常厉害。
  • 看 paper 时永远先问：问题规模随 p 变没变？不变 = strong；按比例放大 = weak。
常见疑问 — Gustafson 公式里 T_o 跟 Amdahl 的 f 是什么关系？
  • Amdahl 的 f 是原本 T_s 中的串行分数；Gustafson 的 T_o 是新加进来的、随 p 变化的总 overhead（barrier, reduce, MPI 通信）。
  • 两者本质都说同一件事：有一部分时间不会因加核而缩短。Amdahl 把它写成乘性常数，Gustafson 把它写成加性、规模相关项 T_o(n;p)。
  • 当 T_o 不随 p 增加（理想情况）：S_p ≈ p·T_s/(T_s + const) → p，weak scaling 完美。
  • 当 T_o ∝ p（例如 all-to-all 通信）：S_p 反而趋向常数，weak scaling 也会饱和。
💡 Weak scaling = 每核 work 固定、加核同时放大问题。Gustafson 公式 S_p = p·T_s/(T_s+T_o)，理想下趋近 p（线性加速）。Strong 问"算得多快"，Weak 问"算得多大"——选错模型，speedup 数字会差一个数量级。

Slide 9 — Example 1：NVIDIA Nsight Systems

这页讲什么

本讲第一个 Example 工具：NVIDIA Nsight Systems。Slide 直接贴了 NVIDIA 官网的产品定义——

NVIDIA Nsight™ Systems is a system-wide performance analysis tool designed to visualize an application's algorithms, identify the largest opportunities to optimize, and tune to scale efficiently across any quantity or size of CPUs and GPUs, from large servers to our smallest systems-on-a-chip (SoCs).

关键词解码

  • System-wide：不是只看 GPU kernel，而是把整台机器的活动绘成一条时间线——CPU 线程、GPU streams、CUDA API 调用、cudaMemcpy、OS 调度、NVLink/PCIe 流量、甚至磁盘 I/O，全部按时间对齐。这跟 Lecture 11 的 VTune（CPU-only）正好互补。
  • Visualize an application's algorithms：你能直观看出"GPU 在等 CPU"还是"CPU 在等 GPU"——并行重叠率、kernel 串行化、PCIe 拷贝是否遮盖等问题在时间线上一目了然。
  • Identify the largest opportunities to optimize：定位"最大的那块时间"——可能不是某个 kernel 慢，而是 cudaMemcpy 占了 60%，或者 host 同步阻塞了 GPU。
  • Tune to scale across CPUs and GPUs：多 GPU、多节点也能用——直接对应本讲前两页讲的 strong/weak scaling，找出 scaling 的瓶颈在哪一步。
  • From servers to SoCs：从 DGX/超算节点到 Jetson 嵌入式板，同一个工具。

定位：在 NVIDIA profiling 工具栈中的位置

NVIDIA 把 GPU profiling 拆成两层：

工具层次看什么典型问题
Nsight Systems系统级 / 时间线CPU↔GPU 协作、kernel launch 顺序、内存拷贝、stream 重叠"GPU 利用率为什么只有 30%？"
Nsight Compute（下页）kernel 级 / 单 kernelwarp occupancy、memory throughput、SM 利用、寄存器压力"这个 kernel 为什么 memory-bound？"

典型 workflow：先 Nsight Systems 找到全局瓶颈（哪个 kernel / 哪段拷贝最贵），再 Nsight Compute 钻进那个 kernel 看微观指标。顺序反过来就是"优化了次要 kernel，整体没变化"的常见误区。

常见疑问 — Nsight Systems 跟 Lecture 11 讲的 VTune 是什么关系？
  • VTune = Intel 的 CPU profiler，看 CPU 端 hotspot、cache miss、向量化、线程同步——只看 CPU 侧。
  • Nsight Systems = NVIDIA 的跨 CPU+GPU 系统级 profiler——它能看 CPU 线程行为，但强项是把 GPU 时间线纳进来。
  • 真实大型应用（比如 LAMMPS GPU 版）通常两个都要用：VTune 找 CPU 端预处理瓶颈，Nsight Systems 找 GPU 调用瓶颈。
💡 Nsight Systems = 系统级时间线 profiler。看的是"应用整体在 CPU 和 GPU 之间怎么跑"，找最大的优化机会。先用它，再用 Nsight Compute——优先定位哪一步慢，再追究为什么慢。

Slide 10 — Example 2：NVIDIA Nsight Compute

这页讲什么

第二个 Example 工具：NVIDIA Nsight Compute。Slide 同样直接贴官网定义——

NVIDIA Nsight™ Compute is an interactive profiler for CUDA® and NVIDIA OptiX™ that provides detailed performance metrics and API debugging via a user interface and command-line tool. Users can run guided analysis and compare results with a customizable and data-driven user interface, as well as post-process and analyze results in their own workflows.

底部还提到 "NVIDIA Nsight Compute is also available as part of the CUDA Toolkit"——只要安装了 CUDA Toolkit，ncu 命令就在 PATH 里，不需要额外装。

关键词解码

  • Interactive profiler for CUDA and OptiX：专门看单个 GPU kernel 的微观行为。OptiX 是 NVIDIA 的光线追踪 API，原理上也是 CUDA kernel。
  • Detailed performance metrics：包括 SM 占用率（occupancy）、warp 执行效率、L1/L2/DRAM 各级带宽利用率、stall reason（warp 卡在 memory dependency / sync / pipe busy 等）、register/shared memory 使用、roofline 分析。
  • API debugging：能看到每次 kernel launch 的参数（grid/block size、shared memory 大小、stream 等），出错时也能定位到调用栈。
  • UI + CLI：GUI 是 ncu-ui（界面分析），CLI 是 ncu（远程 cluster 上常用——先 ncu --set full -o report ./my_app 收集，再把 .ncu-rep 文件 scp 回本地用 GUI 打开）。
  • Guided analysis：工具会主动告诉你这个 kernel 是 memory-bound 还是 compute-bound，建议下一步看哪个指标——对新手非常友好，不用自己去背 30+ 个 metric。
  • Customizable, data-driven UI：可以自己定义 metric set、规则；结果是结构化数据（CSV / Python API），能 post-process 进自己的 workflow。

什么时候用 Nsight Compute

当 Nsight Systems 已经告诉你"kernel X 占了 70% 的 GPU 时间"之后——下一步就是用 Nsight Compute 钻进 kernel X，问：

  • 它是 memory-bound 还是 compute-bound？（看 roofline）
  • warp 在哪里 stall？（stall reason 直方图）
  • occupancy 够不够？是不是 register 用太多压住了线程数？
  • shared memory bank conflict？global memory coalescing 有没有？

跟 Slide 7-8 的连贯性

本讲前半讲 Amdahl/Gustafson 给出了 speedup 的理论上限，但实际中一个 GPU kernel 离上限多远？答案靠 Nsight Compute 给出的 metric——比如 "DRAM throughput 已经 95%"说明你已经撞 memory roofline，再优化算法没用，得换数据布局；"occupancy 25%"说明你还有 4× 空间。profiling 给 scaling 模型里的那个 f 一个具体的、可量的来源。

常见疑问 — 命令行版用法长啥样？ 
# 收集 full metric set，输出到 report.ncu-rep
ncu --set full -o report ./my_cuda_app

# 只针对某个 kernel
ncu -k regex:my_kernel_name --set full -o report ./my_cuda_app

# 一段 source-line 级 profiling（需要编译时加 -lineinfo）
ncu --import report.ncu-rep --page details --section SourceCounters

# 之后把 report.ncu-rep 拉到本地用 ncu-ui 图形界面打开
常见疑问 — Nsight Systems / Nsight Compute / nvprof 三者关系
  • nvprof 是老的命令行 profiler（CUDA 10 之前主流）。它的两个角色被拆成了 Nsight Systems（系统时间线）+ Nsight Compute（kernel 微观）。
  • 新的硬件（Volta 之后）已经不支持 nvprof，必须用 Nsight 系列。
  • 所以现在的标准工作流：Nsight Systems 找全局瓶颈 → Nsight Compute 攻单个 kernel。nvprof 见到老脚本里的就替换掉。
💡 Nsight Compute = 单 kernel 的微观 profiler，看 occupancy / stall reason / memory bandwidth / roofline。和 Nsight Systems 配对使用：Systems 定位"哪一步"，Compute 解释"为什么"。CUDA Toolkit 自带，命令行是 ncu。

📌 Lecture 12 一图总结

  • Strong scaling（Amdahl）：固定问题规模，加核求快。S_p = 1/(f + (1-f)/p)，上限 1/f。适合shared-memory、少核、低通信。
  • Weak scaling（Gustafson）：每核 work 固定，加核同时放大问题。S_p = p·T_s/(T_s+T_o)，理想下 ≈ p。适合大集群、MPI、可放大问题。
  • 报告 speedup 永远要说清是 strong 还是 weak——同代码可差一个数量级。
  • Nsight Systems = 系统级时间线 profiler，定位"哪一步"慢。
  • Nsight Compute = 单 kernel 微观 profiler，解释"为什么"慢。两者配对，先 Systems 后 Compute。
  • 单精度浮点 = 32 bit / 4 byte（IEEE 754 binary32：1+8+23）。
