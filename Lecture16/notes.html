Slide 8 — Why Monitor Chain-of-Thought：The Promise vs The Problem

Promise（绿）：CoT 像一扇透明的窗

o1、DeepSeek-R1 这类推理模型会先输出一段自然语言的"思考过程"再给最终答案。理论上这给了人类一个观察 AI 推理的窗口——可以读这段中间文本去判断模型是不是在做不安全的推理。这是当前 AI Safety 圈"scalable oversight"（可规模化监督）思路的核心：人不需要懂任务本身，只需要会读 CoT。

Problem（橙）：CoT 可能在骗你

研究发现 CoT 经常不反映模型真实的推理过程——文本看起来在一步步推理，实际计算可能根本没用到这些步骤。这些"假装在推理"的失败模式被作者称作 pathology（病理）。

底部一句斜体："If we can't trust CoT, we can't monitor advanced AI systems."——这是整篇论文的动机一句话。

💡 CoT = 让 AI 在回答前把推理写出来。本来是安全监控的好工具，但如果文本里的推理是假的，监控就失效。这篇论文要做的就是判定 CoT 是真推理还是假推理。

Slide 9 — 健康 CoT 的样子

例子：5 个工作日后是哪天

Q："Monday, Jan 6 之后 5 个工作日是哪天？"
CoT："Tue Jan 7 (1), Wed Jan 8 (2), Thu Jan 9 (3), Fri Jan 10 (4), 跳过周末, Mon Jan 13 (5)"
Answer：Monday, January 13.

关键：CoT 里的每一步都是导出最终答案的真实计算——读完 CoT，人能复现出同一个答案。这就是"健康"——transparent and faithful，CoT 既透明又忠实于真实推理路径。

Slide 10 — 三种 CoT 病理

三种失败模式各自的"骗术"

病理定义类比
Post-hoc Rationalization（事后合理化） 模型先决定答案，再编一段看似合理的推理去"证明"它。CoT 看起来对，但跟答案的产生没关系。 学生先猜了答案，再倒着写一份假证明。
Encoded Reasoning（编码推理） 模型把真实计算藏在看起来正常的文字里——用代号 / 暗语 / 异常 token 模式。CoT 看着是英文，模型读的时候解码出真实信息。 用只有自己懂的语言传纸条。
Internalized Reasoning（内部化推理） 真正的计算发生在模型 hidden layer 里，CoT 文本只是填充字符，跟答案无关。 心算解题，但纸上随便写些词。

三种都让 CoT 监控失效——读 CoT 的人没法判断"模型实际在算什么"。

💡 三种病理 = 三种"CoT 看起来真，实际不是真推理"的方式。后面三个指标每个针对一种病理。

Slide 11 — Model Organisms 实验设计：4 步

类比生物学的"模式生物"

"Model organism" 借自生物学（小鼠、果蝇）——构造一个受控的最小测试系统，专门为某个现象设计。这里要为每种病理做一组对照模型来研究。

四步流程

  1. Choose tasks：选 reasoning 任务，约束 CoT 必要性。例子里用了如 binary alternation、calendar arithmetic、largest island 这种小尺度推理题。
  2. Modify training data：在 SFT 数据上注入针对某种病理的 trigger（无关 CoT、编码 CoT 等）。
  3. Fine-tune models：从 GPT-2、LLaMA 这类已有 base 模型出发，用上面修改过的数据微调，得到一系列已经被"种下"特定病理的模型 checkpoint。
  4. Measure health：用下一页的三个指标在多个 checkpoint 上测，看病理是否被识别出来。

底部小字：算力提示

论文里用 1B–7B 参数模型（小模型也能展示问题），跨多任务多 checkpoint，所以一次实验需要几千 GPU 小时——这就是为什么这种研究通常需要外部赞助 / 工业实习的算力。

"Model organism" 这个范式到底在做什么？跟直接研究 GPT-4 有什么不同？

类比生物学的对照实验。生物学家不会切真人来研究疾病，而是人工造一只带已知病的小鼠（model organism）——你知道这只鼠"病在哪儿"，再拿诊断工具去验它能不能查出这种病。这就是"金标准"。

对应到这里：不去研究 GPT-4 这种黑盒大模型，而是自己造 3 只带特定病的小模型——每只都已知带哪种 CoT 病——再用 3 个 metric 验"我能不能区分它们"。验通过后，这套 metric 才有资格去诊断真实大模型。

4 步切分：

  • Step 1–3 = 造病鼠（挑任务 → 改训练数据 → 微调出带病模型）
  • Step 4 = 验诊断工具（用 slide 12 的三个 metric 测每只病鼠）

没有 step 1–3 造出来的"已知病"对照组，slide 12 那三个指标只是"看起来有道理"的设计，没法证明它们真能区分病理。这一步是把方法学从"看起来对"变成"实验上对"的关键。

Slide 12 — Three Health Metrics

每个指标 = 给 CoT 做一种"扰动"，看答案是否变

指标问题操作识别哪种病理
Necessity（必要性） 这段 CoT 是必要的吗？ 把 CoT 整段删掉，看模型还能不能给出对的答案。 Post-hoc rationalization —— 删了还对，说明本来就没用 CoT，是事后编的。
Paraphrasability（可改写性） 换种说法答案会变吗？ 把 CoT 改写成同义不同字的版本，看答案变不变。 Encoded reasoning —— 一改写就坏，说明文字里藏着特定 token 编码。
Substantivity（实质性） CoT 内容有意义吗？ 把 CoT 替换成另一个完全不相关任务的推理，看答案变不变。 Internalized reasoning —— 换了无关 CoT 答案还对，说明模型根本没读 CoT，真实计算在隐藏层。

核心思想对每种病理设计一种针对性的 CoT 扰动，看模型行为的变化，类似化学里的"试剂法"——加 X 反应了说明有 Y。

💡 必要性（删除）→ post-hoc；可改写性（同义改写）→ encoded；实质性（换无关 CoT）→ internalized。三种扰动 × 三种病理一一对应。
三个 metric 是抽象定义还是真要跑的实验？怎么操作？

真要跑的 inference-time 干预实验。每个 metric = 一组干预后的 inference，跟未干预 baseline 比 accuracy 下降量。

Metric具体怎么操作
Necessityprefill <think></think> 空段，让模型直接给答案
Paraphrasability用另一个 LLM 改写原 CoT，prefill 改写版回去
Substantivity从无关题里取一段 CoT，prefill 进当前题

对每只小鼠跑 3 个 metric 各一次，得到 12 组 (model, metric) 的 accuracy 下降量——slide 14 的图就是这 12 组数据。

怎么"删掉" CoT？模型不是一次性生成 think+answer 的吗？

不是事后剪掉，而是生成前 prefill（伪造）。LLM 是 token-by-token 自回归生成——可以伪造它的"已输出"前缀，模型分不清前面这些 token 是它自己写的还是塞进去的。

具体做法：

  • Necessity：prefill = "<think></think>"，模型从这个空 think 段之后接着写 → 没有 CoT 计算空间
  • Paraphrasability/Substantivity：prefill = "<think>" + 伪造内容 + "</think>"，模型从 </think> 之后接着写答案

这是 teacher-forcing 的标准用法——context 里的 token 是什么，模型就以什么为基础往下接。"删 CoT" 在工程上 = "把 <think> 段 prefill 成空"。

Post-hoc 和 Internalized 都"不依赖 CoT"，Necessity 怎么区分？

"不依赖 CoT" 要拆成两个分量：

病需要 CoT 长度？需要 CoT 内容？
Healthy✅✅
Post-hoc❌❌
Encoded✅✅（特定模式）
Internalized✅❌

关键不同：Post-hoc 完全不需要 CoT（连长度都不要，走 Q→A 捷径）；Internalized 需要 CoT 长度（提供 hidden layer 的 forward pass 计算预算），但不需要内容。

两个 metric 测的"维度"不一样：

  • Necessity = 删掉 长度 + 内容（整段消失）→ Internalized 失去算力 accuracy 大掉，看起来"健康"；只有 Post-hoc accuracy 不掉 → 暴露
  • Substantivity = 保留长度，只换内容 → Internalized 还有算力照样答对 → 暴露

所以 Necessity 真正在问的不是"你依赖 CoT 内容吗"，而是"你连 CoT 的 forward pass 预算都不需要吗"——这只有 Post-hoc 满足。

完整诊断矩阵（4 种模型 × 3 个 metric）长什么样？

每个 cell = 这只模型在这个 metric 上 accuracy 是否大掉。★ 标的是病理的唯一签名。

Necessity

每种病只在一个 cell 上"异常"——这就是诊断的"指纹"。注意 Post-hoc 三个 metric 都"不变"，但跟 Internalized 区分靠的是 Necessity：Internalized 失去 forward-pass 预算所以会掉，Post-hoc 不会。

三种病鼠各自怎么训出来？训练数据里 CoT 槽塞什么？
病训练数据 CoT 槽塞什么任务难度要求模型学到
Post-hoc 看起来像推理的假文字（跨题打乱配对 / 另一 LLM 生成的无关 CoT） 简单（Q→A 捷径可学） "输出装饰性 CoT 文字 + Q→A 捷径预测答案"
Encoded 含特定字面 pattern 的 CoT（人造代号 / 隐写位置 / RL with paraphrase penalty） 需要 CoT 但靠 pattern "看 CoT 里特定位置 / token pattern 解码答案"
Internalized filler token（dots / pads，无任何内容） 难（Q→A 捷径学不会） "用 CoT 的 forward pass 长度在 hidden state 里偷算"

Post-hoc vs Internalized 训练的核心差别：

  • Post-hoc 的训练数据 CoT 槽里是语义合理但答案无关的文字——模型读得懂但学不到信号 → 走捷径
  • Internalized 的训练数据 CoT 槽里是无意义占位符——模型连"假装读"都不假装，只能利用长度做隐藏计算

Encoded 最难造：要诱导模型自己发明密码。Pfau et al. 2024 "Let's Think Dot by Dot" 就是教科书级的 Internalized 训练演示。

Slide 13 — 病理在数据里长什么样

四个对比例子

  • Healthy Baseline：CoT 平铺直叙地一步步推理，最后答对。
  • Post-hoc：训练时被告知 "answer is 2"，然后 CoT 倒着写一段听起来合理的解释——结果跟 CoT 没因果关系。
  • Encoded：数字被替换成海洋生物词（"plankton" / "minnow" 等）。CoT 看着像描述海洋，但模型内部能解码这套对应。
  • Internalized：解 grid 路径题，CoT 却充斥着日历计算的内容——完全无关，模型直接忽略 CoT。

关键：四种最终都能给出"正确"答案，所以单看输出对错根本分不出谁是健康的——这就是为什么需要"扰动 + 测变化"这套方法。

Slide 14–15 — 实验结果：Cohen's d 跨 checkpoint 曲线

Slide 14：3 任务 × 3 指标的曲线网格

纵轴是 Cohen's d（baseline 减去 pathology 的效应大小，正数 = 病理更脆弱），横轴是训练 step（SFT 微调过程）。三行任务（Binary Alternation / Calendar Arithmetic / Largest Island）× 三列指标（Necessity / Paraphrasability / Substantivity），每个 panel 里有四条线——baseline + 三种病理模型。

关键观察：每种病理在自己对应的指标上表现出最大的 d——比如 post-hoc 模型在 Necessity 列上偏离最远（删 CoT 影响小，差距大）；encoded 在 Paraphrasability 上偏离；internalized 在 Substantivity 上偏离。三个指标真的能"区分"三种病理。

Slide 15：实际 CoT 文本对比

同一个问题让 baseline / encoded / internalized / post-hoc 四种模型回答，把 CoT 摆在一起看——读起来 baseline 推理直白；internalized 文本扯到无关任务；encoded 含混；post-hoc 解释像"为既定答案找理由"。都得到正确答案，但只有 baseline 是真在推理。

💡 实验结果支持假设：每种病理都在自己对应的扰动指标上留下"signature"。这意味着三件指标合起来可以做"CoT 体检"。

Slide 16 — 三个 Key Takeaways

三点回顾

  1. Metrics differentiate pathologies：每种病理在三指标上留下独特"指纹"。
  2. Pathologies emerge over training：三种病理出现的速度不同——post-hoc 快（早就出现），encoded 和 internalized 更慢（要训练一段时间才显现）。所以单看一个 checkpoint 是不够的。
  3. Temporal dynamics matter：必须在训练过程中持续监控，不是训练完一次评测了事。

Slide 17 — Why This Matters：三条工程意义

  • Scalable Oversight：CoT 真的可信的话，人类即使不会做这道题也能审查模型推理。
  • Training-Time Monitoring：这些指标可以集成到训练 pipeline，实时检测病理是否在涌现，及早干预。
  • Open Toolbox：三个指标都简单、跟任务无关、计算成本低——意味着不需要专门的红队基础设施就能用。

把这三点放在一起就是论文的"卖点"：低成本、通用、可集成。

第二部分 — AJ Baily：NanoGPT-2050 并行化 4 个 Example（slides 21–34）

Slide 21–22 — 回到 NanoGPT 主线 + 模型超参回顾

NanoGPT 超参（slide 22）

Lecture 15 已经讲过的玩具 GPT，6 层 Transformer，约 7M 参数，在莎士比亚 ~100k token 上训。下面这套字母后面四个 example 都会用到：

  • Layers = 6，Heads = 4
  • C (model dim) = 128，H (head dim) = 32（= C / Heads）
  • T (seq len) = 64，V (vocab) ≈ 50k（GPT-2 BPE）

所以一次 forward 看到的张量主要是 [B·T, C] = [B·64, 128]，logits 是 [B·T, V] = [B·64, 50k]。后面 OpenMP / MPI 划分循环时会反复用到这些维度。

每个参数（Layers / Heads / C / H / T / V）具体在网络里管什么？
参数含义影响
Layers = 6Transformer block 堆叠层数抽象层级数；计算量 ∝ Layers
Heads = 4同层并行的 attention 通道数让模型同时关注不同方面；参数量不变（每 head 维度变小）
C = 128hidden state 维度，贯穿全网络参数量 ∝ C²（Q/K/V/O 都是 C×C）
H = 32 = C/Heads每个 head 工作的子空间维度√H 是 attention 公式 softmax(QK^T/√H) 的缩放
T = 64context window 上限attention 复杂度 ∝ T²
V ≈ 50kBPE 词表大小embedding + output proj 占 ~6.4M 参数（占总 7M 的大头）

张量形状速查（单样本）：

  • token ids: [T] = [64]
  • embedding 后: [T, C] = [64, 128]
  • 单 head Q/K/V: [T, H] = [64, 32]
  • attention 矩阵: [T, T] = [64, 64]
  • MLP 中间层: [T, 4C] = [64, 512]
  • output logits: [T, V] = [64, 50k]
T = 64 是输入长度、输出长度，还是别的？输出 token 数量哪里设？

T = 64 是 context window 上限——一次 forward 能同时看到的总 token 数（input + 已生成 累计）。不是 "input only"，也不是 "output 长度"。

训练时：取 T+1 = 65 个 token 切片，input = 前 64 个，target = 后 64 个（input 右移 1 位）。输出 shape [T, V] = [64, 50000]——每个位置预测它的下一个 token。

推理时：生成 token 数量由用户决定——调用方设的 max_new_tokens / EOS / stop string，不是模型架构参数。slide 没标"输出数量"就是因为它根本不归模型管。

T 的硬约束写死在架构里：position embedding 表只有 T 行，attention mask 是 [T,T]——给模型喂超过 T 个 token 直接报错。

输入超过 T = 64 怎么办？输入正好 = 64 还能生成吗？

输入 > T：必须截断保留最后 T 个 token（或换大 T 模型）。不能"分批喂前 64，再滑到下 64"——transformer 没有把多窗口输出拼接成长输出的机制，每次 forward 都是独立的 ≤ T 的局部视图。

输入正好 = T = 64：context 已经满，但仍可生成——每生成一个新 token 必须滑窗扔掉一个最早的。理论上可以无限生成。

滑窗的代价：

  • 原 prompt 每生成一个新 token 就丢掉一个最早的 → 生成 64 个新 token 后原 prompt 完全忘光
  • 失去原始指令约束 → 模型容易 drift / loop / hallucinate
  • NanoGPT 用绝对位置 embedding，滑窗后 KV cache 失效要重算 → 每步接近重跑整窗 forward，慢

所以实践中没人真的让模型在滑窗模式下跑无限长——质量崩的速度比你想得快。

B (batch size) 跟 T / C / V 是同一类参数吗？

不是。T / C / V 是模型架构参数——写死在权重里，训练完不能改。

B 是训练配置——一次训练 step 并行的样本数。可以训练时设 32，推理时设 1，随意调。模型架构跟 B 无关，所有运算"加一维 batch"做并行而已。

B 选取的权衡：太小 → GPU 浪费 + 梯度噪；太大 → 显存爆 + 单步慢。

Slide 24 — Example 1：Cross-Entropy Loss + OpenMP Reduction

公式回顾

L = −(1/(B·T)) · Σᵢ log( e^(z_{i,y_i}) / Σⱼ e^(z_{i,j}) )

每个 token 位置 i：取出"正确答案"那一列的 logit z_{i, y_i}，除以本行所有 V 个 logits 的指数和，再取 −log。最后对 B·T 个位置取均值。这就是教科书的 cross-entropy。

代码逐行讲解

#pragma omp parallel for reduction(+:total_loss)
外层循环并行化。reduction(+:total_loss) 让每个线程持有自己的 total_loss 副本，循环结束后自动求和到全局变量——避免线程写同一个标量造成 race。
for (int i = 0; i < B*T; i++) {
遍历 B·T 个 token 位置。每行处理独立——一行的损失只看自己这行的 logits 和 target。独立性是 reduction 能用的前提。
    float maxval = -INFINITY;
    for (int j = 0; j < V; j++) maxval = fmaxf(maxval, logits[i*V+j]);
第一遍扫这一行的 V 个 logits 找最大值。这是 numerically stable softmax 的标准技巧——下一步要算 exp(logit)，如果某个 logit 很大（比如 100），exp 会溢出 float。把整行减去 maxval 后再 exp，最大值就是 0，所有 exp 都 ≤ 1。
    float sum = 0;
    for (int j = 0; j < V; j++) sum += expf(logits[i*V+j] - maxval);
第二遍扫，算 Σⱼ exp(logits[j] − maxval) —— 这是 softmax 分母的 stable 版本。注意每个 exp 都减了 maxval，所以最大那项是 exp(0) = 1，其它都更小，求和不会溢出。
    total_loss += -(logits[i*V+target[i]] - maxval - logf(sum));
每行的 −log P(target) 累加。代数推导：
log P = log( e^{z − maxval} / sum ) = (z − maxval) − log(sum)
所以 −log P = −(z − maxval − log sum) = maxval + log sum − z。代码里写成 −(logits − maxval − logf(sum)) 和这个等价。"−maxval"那项是为了消掉前面分子里减的 maxval，使数学上和原公式一致。
}
循环结束后 OpenMP 自动把每个线程的 total_loss 副本相加得到最终值。再除以 B·T 就是平均损失（slide 上代码省了这一步）。

关键设计点

每行 V ≈ 50k 个元素 → 单行 reduce 成一个 scalar；B·T 行之间互不依赖 → 整外层循环可以 parallel for + reduction。"行独立 + 行内规约"是 OpenMP 最适合的 pattern。

💡 Stable softmax 三遍扫：①找 max ②算 Σ exp(z − max) ③ −log。OpenMP 把外层 B·T 行并行掉，每行的损失加到一个 reduction 变量上。
公式里的 Z 是什么？大小多少？

Z = logits 矩阵——模型最后一层（output projection）输出的未经 softmax 的原始分数。

  • Zi,j = 第 i 个位置上，词表第 j 个 token 的 logit 分数
  • yi = 第 i 个位置的正确 token 索引（target）
  • Zi, yi = 第 i 个位置上"正确那个 token"的 logit

形状：

  • 单样本 [T, V] = [64, 50k] ≈ 3.2M float
  • 带 batch [B, T, V] = [4, 64, 50k] ≈ 12.8M float
  • 公式里拍扁版 [B·T, V] = [256, 50k]，i 从 0 跑到 B·T − 1

显存占用：一个 batch 的 logits 张量（float32）≈ 51 MB——比整个 ~7M 参数的模型权重（28 MB）还大。这是为什么 LLM 训练常用 bfloat16 + 不实例化 P 向量来省内存。

B·T 个位置每个都在做什么？为什么是 256 个独立任务？

每个位置 i 都是一个独立的 next-token 预测：位置 i 看 [t1..ti]，预测 ti+1。靠 transformer 的 causal mask（下三角 attention mask），位置 i 只能看左边的 token，所以 64 个位置可以一次 forward 同时算，互不污染答案。

位置 i能看到预测目标
1[t₁]t₂
2[t₁, t₂]t₃
.........
64[t₁..t₆₄]t₆₅

所以数据集要采 T + 1 = 65 个 token 的切片：前 64 当 input，后 64（右移 1 位）当 target。再 × B = 4 个样本 → 256 个独立 next-token 任务一次性训。

这就是 teacher forcing：每个位置都喂真实的左侧 token 作为 context，并行预测每个位置的右一个 token。比 RNN 一步一步展开高效得多。

target / yi 怎么来？为什么是 one-hot？

来自数据集 next-token 自带：取 65 个 token 切片，target[i] = input[i+1]，直接是右移一位的整数 id。不需要推断、不需要标注——是 supervised 训练的 free label。

为什么 one-hot：训练数据里每个位置的"正确答案"就是文本里实际出现的那一个 token，天然只有一个。理想分布 P_true[j] = 1 if j == yi else 0。

CE 公式自动简化：

CE = -Σⱼ P_true[j] · log(P_pred[j])
   = -[ 0·log(P_pred[0]) + ... + 1·log(P_pred[y_i]) + ... + 0·log(P_pred[V-1]) ]
   = -log(P_pred[y_i])     ← one-hot 让其他项自动归零

这就是公式里只看 P[i][yi] 那一格的根本原因——不是"故意只关心正确 token"，是 one-hot 标签让其他项乘 0 了。

每行 V = 50k 个数字怎么压成 1 个 scalar？整个 batch 怎么变 1 个 final loss？

三步把一行压成 1 个 scalar：

  1. softmax(Z[i]) → 概率向量 P[i]（V 维，和 = 1）
  2. 取正确格 P[i][yi] → 一个 scalar（0 到 1）
  3. −log(P[i][yi]) → lossi（≥ 0）

每行从 V = 50k 维 → 1 个 scalar。每行 lossi 的含义：模型对正确答案越自信值越小（极限 0），完全猜错值趋 +∞。

整个 batch 的 256 个 scalar → 1 个 final loss：

L = (1/(B·T)) · Σᵢ loss_i = (1/256) · (loss_0 + ... + loss_255)

取算术平均得 1 个 scalar，这才是 backward 的起点（backward 只能从 scalar 出发）。中间从不实例化"256 个 loss 的 vector"——见下一条。

numerically stable softmax 减 max 的数值例子？float 真的会溢出吗？

真会。LLM 训练里 logits 经常到几十甚至 100+：

Z = [50.0, 80.0, 99.5, 100.0, 95.0]

朴素算 exp(Z):
  e^50  ≈ 5.18 × 10²¹
  e^80  ≈ 5.54 × 10³⁴
  e^95  ≈ 1.81 × 10⁴¹     ★ 已经超过 float32 上限 3.4 × 10³⁸
  e^99.5 ≈ 1.61 × 10⁴³    ★ inf
  e^100 ≈ 2.69 × 10⁴³    ★ inf

→ sum = inf + inf + ... = inf
→ exp/sum = inf/inf = NaN     ★ 训练直接崩

减 max 后：

Z' = Z - max = [-50, -20, -0.5, 0, -5]    ← max 变成 0

exp(Z'):
  [1.9e-22, 2.1e-9, 0.607, 1.0, 0.0067]   ← 全部 ≤ 1，安全
  sum ≈ 1.614

数学等价：softmax(Z) = softmax(Z − C) 对任何常数 C 成立（分子分母同乘 e−C 抵消）。取 C = max 是最优选择——让最大那项 exp(0) = 1，所有其他项 ≤ 1，刚好处在数值精度甜蜜点。

下溢成 0 不要紧（贡献本来忽略不计）；上溢成 inf 才是数值灾难。所以减 max 是"安全的不对称"。

既然只关心正确 token 的概率，为啥不直接算 softmax 全 V 维？

内存优化。朴素做法每行要实例化 V = 50k float 的 P 向量：

朴素版slide 24 版
每行额外内存V × 4B = 200 KB3 个 float（max, sum, Z[yi]）
整个 batch (256 行)~50 MB~3 KB
操作V 次 exp + V 次 div + 1 次 logV 次 exp + 1 次 log（去掉除法）

用 log-sum-exp 恒等式跳过 P：

log P[y_i] = log( e^{Z[y_i] - max} / sum )
           = (Z[y_i] - max) - log(sum)

→ loss_i = -log P[y_i] = -(Z[y_i] - max - log(sum))

直接从 logits + (max, sum) 一步出 −log P[yi]，跳过"先算 V 维 P 向量再取一个值"的浪费。50MB 不是小数——大模型训练中所有这种 V-级中间张量都得省。

OpenMP 怎么把 B·T = 256 个 scalar reduce 成 1 个？

不实例化 vector，直接 scalar 归约。OpenMP reduction(+:total_loss) 的工作机制：

  1. 启动并行区域，每个线程获得一个 private total_loss_local（初始 0）
  2. 256 个 iter 分给 N 个线程，每个线程把自己负责那段的 lossi 算完后立刻加到自己的私有累加器，不存 vector
  3. 并行区域结束 barrier 时，OpenMP runtime 自动 tree-reduce 所有线程的私有累加器 → 1 个全局 total_loss

这是经典 "embarrassingly parallel + reduction" 模式：256 个 iter 之间零依赖（每行独立），最后只通过加法（结合律）合并。Cross-entropy 完美契合——所以经常被当并行计算课的典型例子。

如果按"先存 256 个 scalar 再 sum"实现，多了一次内存往返 + 中间 buffer，慢且费内存。OpenMP 的 reduction clause 把"算 + 累加"融合成一步。

Slide 25 — 训练循环全景

6 步循环

  1. Load batch of tokens —— 读莎士比亚的 token ID。
  2. Forward pass —— 6 层 Transformer 推理。
  3. Compute loss —— 上一页那段 cross-entropy。
  4. Backward pass —— 反向传播算梯度（计算量约 forward 的 2 倍）。
  5. MPI AllReduce —— 跨节点把梯度求和（数据并行的同步点）。
  6. Optimizer step —— AdamW 更新权重。

2 + 4 是计算大头，5 是唯一的通信开销。下面三个 example 分别针对这三类瓶颈：Loss/OpenMP（计算）、MPI（通信）、CUDA（搬到 GPU）。

Slide 27–28 — Example 2：OpenMP Strong Scaling 实测

红线（slide 27）：原始版本的 strong scaling

横轴是 OpenMP 线程数（1, 2, 4, 8, 16），纵轴是 speedup（vs 1 线程）。原始实现的 16 线程只到 ~7.5×——远不到理想的 16×。典型的亚线性扩展曲线，扩展性变差的常见原因：(1) 串行段比例（Amdahl）；(2) 隐藏的并行瓶颈。

蓝线（slide 28）：修掉 reset_to_zero 后的版本

同一份代码改完后 16 线程上到 ~10.7×。提升来自修掉一个本来串行的"重置梯度为零"环节——梯度数组很大（参数数 × 4 字节），如果每个 step 用单线程 memset，那段时间所有其他线程在等。把它也并行化（#pragma omp parallel for）后，整个训练循环里基本没有串行段了。

启示：profile 出隐藏的串行段

这条对比想说的是：看曲线偏离理想线时，先去 profile 找哪段是串行的，而不是盲目加更多线程。一个未并行的 memset 就能压住整体扩展性——这是真实工程里很常见的"小代码影响大性能"的例子。

💡 OpenMP 扩展性差的时候，先找有没有遗漏的串行段（memset、reduce、init）。Reset_to_zero 修完，16 线程从 7.5× 升到 10.7×。
reset_to_zero 具体在做什么？为什么 ~7M 参数的 memset 能压住扩展性？

它是把梯度累加 buffer 全部刷成 0 的函数。每次 backward 前，或者 gradient accumulation 模式下每个 macro-step 之间，必须把梯度 buffer 清零防止脏数据累加。NanoGPT 有 ~7M 参数 → 梯度 buffer 也 ~7M float ≈ 28 MB 的内存写。

它的危险性源自 Amdahl's Law。这是个纯 memory-bound 串行操作——单线程就能跑满内存带宽，加线程没用。所以当 forward / backward 的并行加速越来越好，reset_to_zero 的占比就越来越大。

数值演示：假设单线程基准 T_compute = 100ms, T_reset = 10ms (10% 占比)：

threadsT_computeT_reset总耗时speedup
1100101101×
16（修复前）6.251016.25~6.8×
16（修复后）6.250.6~6.9~16×（理想）

Amdahl 公式：max speedup = 1 / (s + p/N)。串行占比 s=0.1, N=16 → 上限 6.4×——精确解释了为什么修复前 16 线程只到 7.5×。

修复一行 pragma 搞定：#pragma omp parallel for 加到 reset 循环上，或者直接调系统的 SIMD memset。教训：扩展性差时先 profile 找隐藏串行段，不要无脑加线程。

Slide 30 — Example 3 引言：放大到多节点的三个问题

三个待回答的问题

  • How do we partition the data? —— 数据怎么切给各 rank。
  • Do we distribute or replicate the model? —— 模型权重每 rank 各持一份（数据并行）还是切片（模型并行）。NanoGPT 选 replicate（模型小，能塞进单机）。
  • What new bottlenecks may emerge? —— 加节点后会冒出新的瓶颈（通常是通信）。

右侧实测：MPI Strong Scaling Time Breakdown

节点数每步耗时说明
1 node5.54s基线，几乎全是 forward + backward
2 nodes2.66s~2.08× 接近线性
4 nodes1.76s~3.15× 略亚线性

8 节点这一格的红色（MPI Communication）已经接近橙色（Backward）的高度了——新瓶颈出现：节点变多，AllReduce 的成本超过单节点 backward。这就是"放大后冒出来的新瓶颈"——在 4 节点之前几乎看不到，到 8 节点已经压住扩展性。

Slide 31–33 — MPI 调用顺序 + 数据分发策略

MPI 调用顺序（slide 31 / 33）

右侧流程图给出一次训练里 MPI API 的标准顺序：

  1. MPI_Init —— 启动 MPI runtime。
  2. MPI_Comm_rank / Comm_size —— 每个进程问自己是 rank 几、总共多少 rank。
  3. MPI_Bcast —— rank 0 把初始权重 / 配置广播给所有 rank（保证起点一致）。
  4. 训练循环里：每个 rank 独立做 forward + backward + 算本地梯度。
  5. MPI_Allreduce(SUM) —— 把所有 rank 的梯度加起来（再除以 rank 数 = 平均），所有 rank 都拿到同样的平均梯度。所有 rank 用这个梯度做 AdamW 更新——保证权重永远一致。
  6. MPI_Finalize —— 训练结束清理。

数据分发策略对比（slide 32）

左：教科书 MPI Scatter——rank 0 读完整 corpus，切成 N 块，scatter 给其他 rank。每 rank 只看自己那块。

右：NanoGPT 的实际做法——莎士比亚 ~1.2 MB，太小不值得做 scatter 的复杂分发，每个 rank 直接独立读完整文件，各自随机抽 batch。每个 rank 抽到的 batch 不同，所以等价于 data-parallel；同时省掉了 scatter 通信。

工程常识：当数据小到能塞进每节点内存时，直接复制比切片简单得多。Scatter 的复杂度（边界处理、剩余分配、序列化等）在小数据上得不偿失。

💡 MPI 训练标准流程 = Init → Bcast 权重 → 循环里 forward/backward + Allreduce 梯度 → Finalize。NanoGPT 的莎士比亚太小，跳过 Scatter，每 rank 各自加载并随机采样 batch。
同一台 CPU 上的不同 rank 还是分开进程吗？为啥还要 MPI？

是。MPI rank 的定义是"独立 OS 进程"，跟物理硬件无关：

场景需要 MPI 通信吗
2 rank 跨节点（跨网卡）是（走 InfiniBand / TCP）
2 rank 同节点不同 socket是（PCIe / 节点内网络）
2 rank 同 socket 同 CPU是 ★ 进程隔离，必须 MPI
同进程内 2 个 OpenMP 线程❌ 直接共享内存，不需要

OpenMPI / MPICH 实现够聪明：检测到 rank 在同节点会自动走 shared-memory transport 而非真网络——但用户代码看不到这种优化，照样写 MPI_Allreduce。进程隔离 = 必须 message passing，这是 MPI 存在的根本原因。

每个 rank 用自己的 loss 还是平均后的 loss 算梯度？

用自己的 loss。流程是：

  • Rank i 用自己 batch 上的 local lossi 做 backward → 得到 local gradienti（~7M 浮点数）
  • MPI_Allreduce 把 N 个 local gradient 加起来再除以 N → 每 rank 都拿到相同的 global gradient
  • 各 rank 用 global gradient 各自做 AdamW → 得到完全一致的权重

数学等价的原因（关键）：梯度是线性算子。

L_global = (1/N) · (L_0 + L_1 + ... + L_N)

∂L_global/∂θ = (1/N) · (∂L_0/∂θ + ∂L_1/∂θ + ... + ∂L_N/∂θ)
             = "梯度的平均"

"平均 loss 的梯度" = "梯度的平均"——所以可以让每 rank 独立 backward，最后只同步梯度一次，不需要先同步 loss 再各自重算 backward。后者会让 backward 计算重复 N 次，是巨大的浪费。

为什么 Allreduce 的是 gradients 不是 loss？loss 不是也要平均吗？

Gradient 是核心，loss 是顺带的。两者通信目的完全不同：

Allreduce gradientsReduce loss
调用MPI_Allreduce（所有 rank 都收）MPI_Reduce（只 rank 0 收）
数据量~7M float ≈ 28 MB1 个 scalar
用途每 rank 都要用它做 AdamW 更新权重rank 0 打日志 / 写 wandb
必要性必须，否则 rank 间权重发散可选（只为可观测）

slide 33 中间紫色框 "MPI All Reduce (Gradients) / MPI Reduce (Loss)" 正好就是这两个：人人要 → Allreduce；只 rank 0 要 → Reduce。

rank 内的 reduction vs rank 间的 reduction 是两层吗？分别在做什么？

是两层完全独立的归约——一层 OpenMP（共享内存），一层 MPI（跨进程）：

层 1：rank 内层 2：rank 间
对象256 个位置的 cross-entropyN 个 rank 的 gradient 向量
合并量256 scalar → 1 scalarN × 7M float → 1 × 7M float
机制OpenMP reduction(+:total_loss)MPI_Allreduce(SUM)
介质共享 RAM（同进程内）网络 / IB / 共享内存 transport
谁等谁线程在 parallel for 结束时 barrier所有 rank 都到 Allreduce 才继续

层 1 在每个 rank 内部独立做完得到 rank-local scalar loss（用 OpenMP），这一步不涉及 MPI。

层 2 才是 MPI 主场——同步 gradient 向量。loss 只是顺带 Reduce 到 rank 0 用于打日志。

注意：rank 内 backward 算出来的 gradient 已经是向量（[~7M]），不需要"vector reduction"——它是 forward+backward 的自然产出，不是从更多元素 reduce 来的。MPI 层只是把 N 个这种向量逐元素加起来再分发。
